Disk Forensics

Disk Imaging

Always work on a forensic copy, never the original evidence. Create bit-for-bit images and verify integrity with hashes.

dd / dcfldd

# Basic disk image with dd
dd if=/dev/sda of=evidence.img bs=4096 conv=noerror,sync status=progress

# Hash while imaging
dd if=/dev/sda bs=4096 conv=noerror,sync | tee evidence.img | md5sum > evidence.md5

# dcfldd — forensic-enhanced dd with built-in hashing
dcfldd if=/dev/sda of=evidence.img bs=4096 hash=md5,sha256 hashlog=hashes.txt

# Split into chunks
dcfldd if=/dev/sda of=evidence split=2G splitformat=000 hash=sha256

# Verify image integrity
md5sum evidence.img
sha256sum evidence.img

FTK Imager (Windows)

GUI-based forensic imager. Supports E01 (EnCase), AFF, raw (dd) formats. Generates hash verification automatically. Can also mount images for read-only browsing.

# Mount E01 image on Linux with ewfmount
ewfmount evidence.E01 /mnt/ewf/
mount -o ro,loop /mnt/ewf/ewf1 /mnt/evidence/

# Convert E01 to raw

File Systems

Ext4 Structure

ComponentDescription
SuperblockFS metadata — block size, inode count, mount time. Backup copies at block group boundaries.
Block Group DescriptorPointers to block/inode bitmaps and inode table for each group.
Inode TableEach inode stores permissions, timestamps, size, data block pointers. No filename — that's in the directory entry.
ExtentsExt4 uses extent trees instead of indirect blocks. Each extent maps a contiguous range of logical blocks to physical blocks.
JournalLogs metadata (and optionally data) changes before committing. Recovery goldmine — contains deleted file metadata.
# Superblock info
dumpe2fs /dev/sda1 | head -50
tune2fs -l /dev/sda1

# List inodes
debugfs /dev/sda1
debugfs: ls -l /
debugfs: stat <inode_number>
debugfs: cat <inode_number>

# Recover deleted files via journal
debugfs: lsdel              # list recently deleted inodes
debugfs: dump <inode> /tmp/recovered_file

NTFS Structure

ComponentDescription
$MFTMaster File Table — one record (1024 bytes) per file/dir. Contains all metadata and small file data (resident).
$MFT EntryHeader + attributes: $STANDARD_INFORMATION, $FILE_NAME, $DATA, $INDEX_ROOT, $INDEX_ALLOCATION.
$LogFileTransaction journal for NTFS metadata. Records create/delete/rename operations.
$UsnJrnlUSN Change Journal — logs every file/dir change with reason codes. Located at $Extend\$UsnJrnl:$J.
$BitmapCluster allocation bitmap. Shows which clusters are in use.

FAT32 Structure

ComponentDescription
Boot SectorVolume info, cluster size, FAT location, root dir cluster.
FAT (File Allocation Table)Linked list of clusters per file. Entry = next cluster number, 0x0FFFFFFF = end-of-chain, 0x00000000 = free.
Directory Entry32 bytes: 8.3 filename, attributes, timestamps, starting cluster, file size. Deleted files have 0xE5 as first byte.
Data AreaActual file content in clusters. Slack space between end-of-file and end-of-cluster can contain remnant data.

File Carving

Recovers files from raw disk images by scanning for known file signatures (magic bytes), ignoring filesystem metadata entirely.

# foremost — carve by file headers/footers
foremost -t all -i evidence.img -o /output/foremost/
foremost -t jpg,png,pdf,doc,zip -i evidence.img -o /output/foremost/

# scalpel — faster, config-driven carving
# Edit /etc/scalpel/scalpel.conf to uncomment desired file types
scalpel -c /etc/scalpel/scalpel.conf -o /output/scalpel/ evidence.img

# binwalk — firmware/embedded file extraction
binwalk evidence.img                    # scan for signatures
binwalk -e evidence.img                 # extract embedded files
binwalk --dd='.*' evidence.img          # extract everything

# bulk_extractor — carves emails, URLs, credit cards, etc.
bulk_extractor -o /output/bulk/ evidence.img

Alternate Data Streams (ADS)

NTFS allows multiple data streams per file. The default (unnamed) stream is what you normally see. Additional named streams are hidden from normal directory listings.

# Windows — create and read ADS
echo "hidden data" > normal.txt:secret.txt
more < normal.txt:secret.txt
dir /r                                    # shows ADS entries

# Detect ADS with Sleuth Kit
fls -r evidence.img | grep -i ":"

# Extract ADS
icat -o <offset> evidence.img <inode>:<stream_name> > extracted_ads

$LogFile and $UsnJrnl

# Extract $LogFile
icat -o <offset> evidence.img 2 > '$LogFile'

# Parse USN Journal
# Extract $UsnJrnl:$J
icat -o <offset> evidence.img <usnjrnl_inode>-128-4 > usnjrnl.bin

# Parse with usnjrnl_parse or MFTECmd
python usnjrnl_parse.py -f usnjrnl.bin -o usnjrnl.csv

Anti-Forensics Detection

TechniqueDetection Method
TimestompingCompare $STANDARD_INFORMATION vs $FILE_NAME timestamps in MFT. $FN timestamps can only be modified by the kernel.
File wipingLook for overwrite patterns (all zeros, random data) in unallocated space. Tools like sdelete leave artifacts in Prefetch/USN Journal.
Log clearingEvent ID 1102 (Security log cleared), gaps in log timestamps, missing expected events.
Hidden partitionsCompare disk size reported by mmls vs physical size. Check for HPA/DCO with hdparm.
SteganographyStatistical analysis of image files (chi-square, RS analysis). Tools: stegdetect, zsteg, steghide.
EncryptionHigh entropy in file/partition data. Look for known headers (LUKS, BitLocker, VeraCrypt).
Data hiding in slackCompare file size in directory entry vs allocated clusters. Examine cluster slack with blkcat.
# Detect timestomping with analyzeMFT
analyzeMFT.py -f '$MFT' -o mft.csv
# Compare SI_Created vs FN_Created columns — large discrepancies = timestomping

# Entropy analysis for encrypted/wiped areas
ent suspicious_file            # check randomness
binwalk -E evidence.img        # entropy graph

# Detect known wiping tool artifacts
grep -r "sdelete" prefetch/
grep -r "eraser" prefetch/
grep -r "ccleaner" prefetch/

Challenge 7: Recycle Bin Forensics

Easy

The suspect "deleted" a sensitive document, but it's still in the Recycle Bin. Parse the $I metadata file to find the original path and recover the content from the $R file.

# Setup — create mock $I and $R files
import struct
import datetime

# $I file format (Windows 10+):
# 0x00: Version (2, 8 bytes)
# 0x08: File size (8 bytes)
# 0x10: Deletion timestamp (FILETIME, 8 bytes)
# 0x18: Filename length (4 bytes)
# 0x1C: Original path (UTF-16LE)

original_path = r"C:\Users\suspect\Documents\FLAG{recycle_bin_treasure}.docx"
path_bytes = original_path.encode('utf-16-le')
filetime = 133500000000000000  # ~Jan 2024

with open('$IABCDEF.docx', 'wb') as f:
    f.write(struct.pack('<Q', 2))               # version
    f.write(struct.pack('<Q', 15234))            # file size
    f.write(struct.pack('<Q', filetime))          # deletion time
    f.write(struct.pack('<I', len(original_path)))# path length
    f.write(path_bytes)                           # original path

# $R file contains the actual file content
with open('$RABCDEF.docx', 'w') as f:
    f.write("Document content with FLAG{recycle_bin_treasure}")

Parse the $I file to get the original path and deletion timestamp. Read bytes at offset 0x1C as UTF-16LE for the original filename. The matching $R file (same suffix) contains the actual file data. Use RBCmd.exe or the Python struct module to parse.
