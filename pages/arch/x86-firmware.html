Secure Boot

  • How it works: Firmware verifies signatures of boot loader and drivers before execution
  • Keys: PK (Platform Key), KEK (Key Exchange Key), DB (Authorized Signatures), DBX (Forbidden Signatures)
  • Signature Check: Verify .efi binary against X.509 certificates in DB
  • Bypass Techniques:
    • Disable Secure Boot (if allowed by TPM)
    • UEFI variable tampering (if SMM doesn't protect it)
    • Firmware vulnerabilities (flashing unsigned firmware)
    • Supply chain attacks (compromised signing keys)

System Management Mode (SMM)

SMM is the most privileged execution mode on x86 — sometimes called "Ring -2". It runs invisible to the OS, hypervisor, and all software.

Overview

  • Entry: CPU enters SMM via System Management Interrupt (SMI). All logical processors freeze and enter SMM simultaneously
  • SMRAM: dedicated memory region (typically 8 MB at TSEG) inaccessible from Ring 0. Contains SMI handler code and save state
  • Exit: RSM instruction restores all CPU state and returns to the interrupted context
  • Trigger: write to APMC port (0xB2) or hardware events (thermal, chipset errors)

SMRAM Layout

TSEG (Top Segment — typical SMRAM region):
┌──────────────────────────────────────────────┐
│ SMBASE + 0x00000   SMI Handler Code          │
│                    (firmware SMM modules)     │
├──────────────────────────────────────────────┤
│ SMBASE + 0xFE00    SMM Save State Area       │
│                    (all register values       │
│                     saved on SMI entry)       │
├──────────────────────────────────────────────┤
│ SMBASE + 0xFFFC    SMM Revision ID           │
└──────────────────────────────────────────────┘

Default SMBASE = 0x30000 (relocated by firmware to TSEG during init)

SMM Security Mechanisms

ProtectionRegisterPurpose
D_LCKSMRAM ControlLocks SMRAM configuration — prevents reopening SMRAM from OS
SMRRIA32_SMRR_PHYSBASE/MASKSMM Range Registers — defines cacheable SMRAM region, prevents cache-based SMRAM access attacks
SMM_BWPBIOS Control (BC)SMM BIOS Write Protect — only SMM code can write to BIOS flash region
BLEBIOS Control (BC)BIOS Lock Enable — generates SMI when BIOSWE is set, allowing SMM to clear it

SMM Vulnerabilities

  • Callout: SMI handler reads function pointer from memory outside SMRAM → attacker with Ring 0 overwrites it → code execution in SMM
  • TOCTOU: SMI handler validates a buffer, then uses it later — attacker modifies buffer between check and use
  • Confused Deputy: SMI handler performs privileged action (flash write) based on unvalidated input from the OS
  • Cache Poisoning (pre-SMRR): fill cache with malicious code at SMRAM addresses before SMI, CPU executes from cache

ACPI (Advanced Configuration and Power Interface)

ACPI tables are data structures passed from firmware to the OS describing hardware configuration, power management, and device topology.

Table Hierarchy

RSDP (Root System Description Pointer)
  │  Found via UEFI System Table or BIOS scan (0xE0000–0xFFFFF)
  │  Contains pointer to RSDT (32-bit) or XSDT (64-bit)
  │
  ├── XSDT (Extended System Description Table)
  │     Array of 64-bit pointers to all other ACPI tables
  │
  ├── FADT (Fixed ACPI Description Table)
  │     Hardware feature flags, PM timer, GPE registers
  │     Points to DSDT
  │
  ├── DSDT (Differentiated System Description Table)
  │     Main AML (ACPI Machine Language) bytecode
  │     Describes devices, methods, thermal zones, power states
  │
  ├── SSDT (Secondary System Description Table)
  │     Additional AML code (CPU P-states, dynamic devices)
  │
  ├── MADT / APIC (Multiple APIC Description Table)
  │     Processor topology: LAPIC IDs, IOAPIC addresses, NMI sources
  │     Determines CPU count visible to OS
  │
  ├── MCFG (Memory Mapped Configuration)
  │     PCIe ECAM/MMCFG base address (PCIEXBAR)
  │
  ├── HPET (High Precision Event Timer)
  │     HPET register base address and capabilities
  │
  ├── DMAR (DMA Remapping Table)
  │     Intel VT-d / IOMMU configuration
  │     DRHD (DMA Remapping Hardware Unit Definition)
  │     Required for Kernel DMA Protection
  │
  ├── BGRT (Boot Graphics Resource Table)
  │     OEM boot splash image
  │
  └── SLIT/SRAT (NUMA topology tables)

Key Tables for Security

TableSecurity Relevance
DMARIOMMU/VT-d config — without it, DMA attacks succeed. Check for DRHD entries covering all PCI segments
MADTProcessor enumeration — a rogue entry could cause crashes or reveal hidden cores
DSDT/SSDTAML bytecode executed by OS — malicious AML can call SMI, manipulate hardware. Firmware rootkits may modify these
MCFGPCIe MMCFG base — if wrong/absent, extended PCIe config space is inaccessible
WSMTWindows SMM Security Mitigations Table — declares SMM is hardened against callouts

SPI Flash & BIOS Regions

System firmware is stored on a SPI (Serial Peripheral Interface) flash chip. The flash is divided into regions controlled by the chipset.

Flash Layout

SPI Flash (typical 16-32 MB):
┌──────────────────────────────┐ 0x00000000
│ Flash Descriptor (4 KB)      │ ← Master region, defines layout + access rules
├──────────────────────────────┤
│ Intel ME Region              │ ← Management Engine firmware (off-limits to OS)
│ (1-8 MB)                     │
├──────────────────────────────┤
│ GbE Region (optional)        │ ← Gigabit Ethernet NVM
│ (8 KB)                       │
├──────────────────────────────┤
│ Platform Data                │ ← OEM configuration data
├──────────────────────────────┤
│ BIOS Region                  │ ← UEFI firmware (DXE, PEI, SEC volumes)
│ (4-24 MB)                    │   Contains NVRAM (UEFI variables)
└──────────────────────────────┘ End of flash

Flash Protection Bits

Register/BitLocationPurpose
FLOCKDNSPI HSFSFlash Lockdown — locks SPI controller config, prevents region access changes
BIOSWEBIOS Control (BC)BIOS Write Enable — 0=BIOS region write-protected, 1=writable from OS
BLEBIOS Control (BC)BIOS Lock Enable — triggers SMI when BIOSWE is set, allowing SMM to block it
SMM_BWPBIOS Control (BC)SMM BIOS Write Protect — only SMM can write BIOS region (even if BIOSWE=1)
PR0-PR4SPI Protected RangeProtected Range registers — hardware write-protect specific flash address ranges
FDOPSSFlash DescriptorFlash Descriptor Override Pin-Strap Status — manufacturing mode override

Proper configuration: BIOSWE=0, BLE=1, SMM_BWP=1, FLOCKDN=1, PR registers covering critical regions.

Intel ME / CSME

The Intel Management Engine (ME) / Converged Security and Management Engine (CSME) is an independent microcontroller embedded in the PCH that runs its own firmware and OS (MINIX-based), with access to main memory, network, and all platform resources.

Architecture

  • Processor: Dedicated x86 core (Minute IA / Sparc core on older platforms) inside the PCH
  • Memory: Own SRAM + can access system DRAM via UMA (reserved region invisible to OS)
  • Firmware: Stored in SPI flash (ME region), signed by Intel
  • Communication: HECI/MEI (Host Embedded Controller Interface) — PCI device, typically 00:16.0
  • Always on: Runs whenever power is connected (even when OS is off)

ME Components

ComponentPurpose
AMTActive Management Technology — remote KVM, power control, BIOS access over network (enterprise only)
Boot GuardHardware root of trust — verifies IBB (Initial Boot Block) against OTP fuses before CPU executes any code
PTTPlatform Trust Technology — firmware-based TPM 2.0 (fTPM)
PAVPProtected Audio/Video Path — DRM decryption in isolated environment
ICCIntegrated Clock Controller — manages platform clocking

Security Concerns

  • Full access to DRAM, network, and USB — a compromised ME is a persistent, invisible backdoor
  • Black-box firmware (Intel-signed, encrypted) — cannot be audited by users
  • Known vulnerabilities: SA-00086 (RCE via JOM), SA-00125 (auth bypass in AMT)
  • Partial mitigation: Intel provides HAP bit (High Assurance Platform) or me_cleaner to disable non-essential ME modules

Intel Boot Guard

Hardware-based verified boot chain. Cannot be disabled once OEM burns the fuses — provides root of trust that software cannot subvert.

Boot Guard Profiles

ProfileDescription
Measured BootME measures IBB into TPM PCRs. Does NOT prevent boot — just records measurements for remote attestation
Verified BootME verifies IBB signature against OTP-fused public key hash. Boot halts if verification fails
Verified + MeasuredBoth: verify signature AND record measurements

Boot Guard Chain

1. Power On
2. ME/CSME runs ACM (Authenticated Code Module) from ROM
3. ACM reads IBB (Initial Boot Block) from SPI flash
4. ACM verifies IBB signature against OTP-fused key hash
   ├── Match → boot continues, SEC phase executes
   └── Mismatch → platform halts (verified boot) or logs failure
5. IBB (SEC phase) verifies PEI → PEI verifies DXE → chain continues

Key points:
- OTP fuses cannot be changed after manufacturing
- Even reflashing SPI won't bypass it — wrong signature = no boot
- Different from Secure Boot (UEFI level, key database modifiable)

# Bits 0-7 indicate Boot Guard profile

I/O Access Methods

x86 platforms provide multiple mechanisms for the CPU to communicate with hardware devices. Understanding these is critical for firmware security research and CTF challenges involving hardware interaction.

Port I/O (PIO)

Legacy x86 I/O mechanism using a separate 64 KB I/O address space (0x0000–0xFFFF) accessed via IN/OUT instructions.

Port RangeDeviceUsage
0x0020-0x0021PIC (8259A Master)Interrupt controller (legacy, replaced by APIC)
0x0040-0x0043PIT (8254 Timer)Programmable Interval Timer
0x0060, 0x0064PS/2 ControllerKeyboard/mouse (also used for A20 gate, system reset)
0x0070-0x0071CMOS/RTCReal-time clock + NVRAM (BIOS settings)
0x00B2APMCAdvanced Power Management Control — triggers SMI
0x00B3APM StatusSMI data port
0x0CF8PCI CONFIG_ADDRESSSelect PCI device/register for config access
0x0CFCPCI CONFIG_DATARead/write selected PCI config register
0x03F8COM1 (Serial)UART serial port (debug output)
0x0080POST CodeDiagnostic port — BIOS writes progress codes during boot

PIO Access Instructions

; Read 1 byte from port 0x64 (PS/2 status)
mov   dx, 0x64
in    al, dx          ; AL = byte read from port

; Write 1 byte to port 0xB2 (trigger SMI)
mov   dx, 0xB2
mov   al, 0x00        ; SMI command byte
out   dx, al          ; Triggers System Management Interrupt

; Read 4 bytes (DWORD) from PCI CONFIG_DATA
mov   dx, 0xCFC
in    eax, dx          ; EAX = 32-bit PCI config register value

; String I/O (repeat)
mov   dx, 0x1F0       ; IDE data port
mov   edi, buffer
mov   ecx, 256        ; 256 DWORDs = 1 sector
rep   insd            ; Read 512 bytes from disk controller

PIO Access Control

  • IOPL (EFLAGS bits 13:12): if CPL > IOPL, IN/OUT check the TSS I/O Permission Bitmap
  • TSS I/O Bitmap: 65536 bits (8 KB), one per port. Bit=0 means port accessible, Bit=1 means #GP
  • Linux: ioperm(port, num, 1) or iopl(3) to grant user-mode port access (requires CAP_SYS_RAWIO)
  • CHIPSEC: python3 chipsec_util.py io read 0xCF8 4

Memory-Mapped I/O (MMIO)

Devices map their registers into the physical address space. CPU accesses them with normal MOV instructions (load/store). No special I/O instructions needed.

Key MMIO Regions

Flash (BIOS)0xFF000000-0xFFFFFFFF16 MBSPI flash mapped at top of 4 GB (decode by chipset)

MMIO vs RAM

  • Caching: MMIO regions must be marked uncacheable (UC) or write-combining (WC) in MTRRs/PAT — otherwise stale cache values cause incorrect device behavior
  • Side effects: reads from MMIO can change device state (e.g., reading a status register clears it). Compiler must not optimize away MMIO accesses — use volatile in C or readl()/writel() in Linux
  • MTRR (Memory Type Range Registers): MSRs that define caching policy for physical address ranges. IA32_MTRR_PHYSBASE0/IA32_MTRR_PHYSMASK0, etc.
  • PAT (Page Attribute Table): per-page caching control via PTE bits (PWT, PCD, PAT)

DMA (Direct Memory Access)

Devices can read/write physical memory directly without CPU involvement. Critical security concern — a malicious device can compromise the entire system.

  • Without IOMMU: any bus-master device can DMA read/write ALL physical memory (kernel code, credentials, page tables)
  • With IOMMU (Intel VT-d / AMD-Vi): DMA is restricted to assigned memory regions via second-level page tables
  • Attack tools: PCILeech (FPGA), Inception (Thunderbolt/PCIe), Thunderclap
  • Defense: Kernel DMA Protection (Win10 1803+), IOMMU strict mode, Thunderbolt security levels

PCI Topology

  • Bus: PCI has up to 256 (8 bits to encode)
    • PCI Bridge: used to connect PCI buses
    • PCI Switch: same as bridge but for PCIe (note: if using PCIe to PCI use a bridge)
    • Bus 0: used by Intel/AMD CPU/PCH/ICH/MCH-internal hardware blocks
  • Device: each bus has up to 32 (5 bits to encode)
  • Function: each device has up to 8 (3 bits to encode)

Labs

Lab 1: BIOS/UEFI Boot Mode Identification

Easy

Objective: Determine your system's firmware type, verify Secure Boot status, and examine UEFI variables.

# Linux: Check UEFI vs Legacy BIOS
ls /sys/firmware/efi/
# Directory exists → UEFI mode. Missing → Legacy BIOS.

# Detailed boot info
bootctl status
efibootmgr -v

# Secure Boot state
cat /sys/firmware/efi/efivars/SecureBoot-*/data | xxd | head -1
# Last byte: 01 = enabled, 00 = disabled

# List all UEFI variables
ls /sys/firmware/efi/efivars/ | head -20
# Windows: Check boot mode and Secure Boot
Confirm-SecureBootUEFI
bcdedit /enum firmware
Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\SecureBoot\State"
msinfo32  # System Summary → BIOS Mode, Secure Boot State

Tasks:

  1. Determine if your system boots UEFI or Legacy BIOS. On Linux, check for /sys/firmware/efi/. On Windows, check msinfo32 → BIOS Mode.
  2. Verify Secure Boot status. If disabled, explain the security implications (unsigned boot loaders can execute).
  3. List 5 UEFI variables and identify their purpose (e.g., BootOrder, SecureBoot, SetupMode).
  4. Check SetupMode — if it's 1, Secure Boot keys can be modified without authentication. Why is this dangerous?

Lab 2: PCI Device Enumeration & Config Space Decoding

Medium

Objective: Enumerate PCI devices, dump configuration space headers, and decode key fields (VID/DID, BAR, Command register) using both OS tools and CHIPSEC.

# Linux: Enumerate all PCI devices
lspci -nn          # Show VID:DID
lspci -vvv -s 00:1f.0   # Verbose dump of LPC controller
lspci -xxx -s 00:00.0   # Full hex dump of Host Bridge config space

# Direct sysfs access
xxd /sys/bus/pci/devices/0000:00:1f.0/config | head -4

# CHIPSEC (requires root + kernel module)
python3 chipsec_util.py pci enumerate
python3 chipsec_util.py pci dump 0 31 0     # Bus 0, Dev 31, Func 0
python3 chipsec_util.py pci read 0 0 0 0x00  # Read VID at offset 0x00

Tasks:

  1. Enumerate all PCI devices. Find your NIC, USB controller, and SATA controller — note their BDF (Bus:Device.Function) addresses.
  2. Dump the full 256-byte config header for Bus 0, Device 0 (Host Bridge). Use the PCI Config Header diagram on this page to decode: VID (0x00-0x01), DID (0x02-0x03), Command (0x04-0x05), Class Code (0x0B).
  3. Read BAR0-BAR5 for your NIC. Determine if each BAR is Memory-mapped or I/O, 32-bit or 64-bit, and whether it's prefetchable. Use the BAR decoder tool on this page.
  4. Check the Command register: are I/O Space (bit 0), Memory Space (bit 1), and Bus Master (bit 2) enabled? What happens if Bus Master is disabled for a NIC?

Lab 4: ACPI Table Exploration

Medium

Objective: Read and interpret ACPI tables provided by firmware — understand how the OS discovers hardware configuration at boot.

# Linux: List all ACPI tables
ls /sys/firmware/acpi/tables/
# Common: DSDT, SSDT*, MADT, FADT, HPET, MCFG, DMAR

# Dump and disassemble DSDT (main hardware description)
sudo cat /sys/firmware/acpi/tables/DSDT > /tmp/dsdt.dat
iasl -d /tmp/dsdt.dat
less /tmp/dsdt.dsl

# Check MADT for processor topology
sudo cat /sys/firmware/acpi/tables/APIC > /tmp/madt.dat
hexdump -C /tmp/madt.dat | head -20

# Check MCFG for PCIe MMCFG base address
sudo cat /sys/firmware/acpi/tables/MCFG > /tmp/mcfg.dat
hexdump -C /tmp/mcfg.dat

# Check DMAR for IOMMU/VT-d configuration
sudo cat /sys/firmware/acpi/tables/DMAR > /tmp/dmar.dat
hexdump -C /tmp/dmar.dat | head -20

Tasks:

  1. List all ACPI tables on your system. Identify DSDT (main device tree), MADT (interrupt/processor info), FADT (fixed hardware), MCFG (PCIe config base).
  2. Disassemble DSDT with iasl. Find the _SB (System Bus) scope and identify PCI root bridge and processor objects.
  3. Parse MCFG to find the PCIEXBAR (PCIe MMCFG base address). Use the MMIO converter on this page to verify you can decode BDF from MMIO addresses using that base.
  4. Check DMAR table — does your system have VT-d/IOMMU configured? Are there DRHD (DMA Remapping Hardware Unit) entries? This determines whether Kernel DMA Protection is possible.

CTF Challenges

Challenge 1: Decode the PCI Config Dump

Easy

Given a PCI configuration space hex dump, identify the device vendor, device ID, and what type of device it is. Flag format: FLAG{vendor_devicetype}.

# PCI config header dump (first 16 bytes):
# 00: 86 80 A2 09 06 04 10 00 05 00 00 06 00 00 00 00
#
# Decode:
# Bytes 0x00-0x01 (little-endian): VID = 0x8086 → ???
# Bytes 0x02-0x03 (little-endian): DID = 0x09A2 → ???
# Byte 0x0B: Class Code = 0x06 → ???
# Byte 0x0A: Subclass = 0x00 → ???
#
# Use the VID/DID decoder on this page to look up the device.

VID 0x8086 = Intel Corporation. Class 0x06 = Bridge Device. Subclass 0x00 = Host Bridge. This is the CPU's PCI Host Bridge (DRAM Controller). Use the VID/DID decoder tool on this page to identify the specific product name from DID 0x09A2.

Challenge 2: Find the Unlocked SPI Flash

Medium

You're auditing a system's firmware security. Given CHIPSEC output, determine if the SPI flash is write-protected. If not, explain the attack surface. Flag: FLAG{unprotected_register_name}.

# CHIPSEC output:
# [*] Running module common.bios_wp
# [*] BIOS Region Write Protection:
#     BIOS Control Register (BC) = 0x00000089
#       BIOSWE (BIOS Write Enable)          = 1   ← !!!
#       BLE (BIOS Lock Enable)              = 0   ← !!!
#       SMM_BWP (SMM BIOS Write Protection) = 0   ← !!!
#       TSS (Top Swap Status)               = 0
# [-] FAILED: BIOS region write protection is not enabled!
#
# What registers need to be set to protect the BIOS region?
# What attack is possible with BIOSWE=1 and BLE=0?

BIOSWE=1 means the BIOS region of SPI flash is writable from the OS. BLE=0 means the chipset won't generate an SMI when someone tries to set BIOSWE — so there's no SMM protection. SMM_BWP=0 means even SMM doesn't enforce write protection. This means any Ring 0 code (kernel driver, rootkit) can reflash the BIOS with a firmware implant that survives OS reinstallation. Properly secured systems have BIOSWE=0, BLE=1, SMM_BWP=1. FLAG{BIOSWE}.

Challenge 3: PCIe DMA Attack Simulation

Hard

A malicious PCIe device has DMA access to physical memory. Given the system has no IOMMU protection, describe the attack chain to read kernel memory. What register/table would you target first?

# Scenario: System with DMA protection DISABLED
# Attacker has a PCILeech-compatible FPGA board in a Thunderbolt/M.2 slot
#
# Attack steps:
# 1. Device issues DMA read to physical address range
# 2. Without IOMMU, the DMA controller grants access to ALL physical memory
# 3. Scan physical memory for known signatures:
#    - NT kernel header ("MZ" + "PE" at known offsets)
#    - EPROCESS structures (scan for known field patterns)
#    - Page tables (CR3 values from interrupt frames)
#
# Tools: pcileech, inception, thunderclap
# pcileech.exe dump -min 0x1000 -max 0x10000000 -out memdump.raw
#
# Defense: Enable IOMMU (VT-d on Intel, AMD-Vi on AMD)
# Check: msinfo32 → Kernel DMA Protection
#
# What would you target first?
# FLAG{IDT_or_GDT_physical_address}

The IDT (Interrupt Descriptor Table) is at a fixed physical address per boot and contains function pointers for every interrupt handler. Reading it gives you kernel code addresses (defeating KASLR). From there, find ntoskrnl base, locate EPROCESS list, read/modify tokens. Defenses: (1) IOMMU/VT-d restricts DMA to assigned memory regions, (2) Kernel DMA Protection (Win10 1803+) enables IOMMU by default for external devices, (3) Thunderbolt security levels can block unauthorized devices.

Challenge 4: SMM Callout Vulnerability

Hard

An SMI handler in the firmware has a callout vulnerability — it calls a function pointer stored outside SMRAM. Describe how to exploit this for persistent firmware compromise.

# CHIPSEC detected an SMM callout:
# [*] Running module common.smm
# [-] SMI handler at SMRAM+0x4200 reads function pointer from
#     physical address 0xBFF00100 (outside SMRAM!)
#
# Attack chain:
# 1. From Ring 0 (kernel driver): write controlled address to 0xBFF00100
# 2. Trigger SMI (e.g., write to APMC port 0xB2)
# 3. SMI handler enters SMM (Ring -2), reads 0xBFF00100, calls it
# 4. Attacker code now executes in SMM context — full platform access
# 5. Modify SPI flash to install persistent firmware implant
#
# Why is this worse than kernel compromise?
# SMM survives OS reinstall and runs below the hypervisor
#
# CHIPSEC module: chipsec_main.py -m tools.smm.smm_ptr
# FLAG{SMM_callout_persistent_implant}

SMM (System Management Mode) runs at "Ring -2" — below the OS kernel and hypervisor. SMRAM is supposed to be locked (SMRAM Lock bit in chipset config), but if an SMI handler reads a function pointer from memory outside SMRAM, an attacker with kernel access can control that pointer. When the SMI fires, the handler calls the attacker's code in SMM context, giving access to: SPI flash (firmware reflashing), chipset configuration registers, and all physical memory. This is the most persistent implant possible — it survives OS reinstall, disk wipe, and even hypervisor-based security.

Challenge 5: MMCFG Address Calculation

Easy

Given PCIEXBAR = 0xE0000000, calculate the MMIO address for Bus 0, Dev 31, Func 0, Offset 0x100. Flag: FLAG{mmio_address}.

# MMIO = PCIEXBAR + (Bus << 20) + (Dev << 15) + (Func << 12) + Offset
# = 0xE0000000 + (0 << 20) + (31 << 15) + (0 << 12) + 0x100
# = 0xE0000000 + 0x000F8000 + 0x100 = ???
# Use the converter tool on this page to verify!

0xE0000000 + 0x000F8000 + 0x100 = 0xE00F8100. FLAG{0xE00F8100}.

Challenge 6: Identify the Secure Boot Bypass

Medium

Given: SecureBoot=1, SetupMode=0, PK set to OEM cert, dbx has 50 entries. Attacker has physical access. Find the most practical bypass. Flag: FLAG{bypass_technique}.

# Options:
# A) Replace PK (requires Setup Mode)
# B) Boot unsigned USB (blocked by Secure Boot)
# C) Use vulnerable signed boot loader not in dbx
# D) Disable Secure Boot in BIOS setup
# E) Clear CMOS to reset all BIOS settings

With physical access: clear CMOS (E) resets everything including BIOS password and Secure Boot. Software-only: use a known-vulnerable but signed boot loader not yet in dbx (C), like BlackLotus used CVE-2022-21894. FLAG{CMOS_clear_or_vulnerable_signed_loader}.

; 0x800F8F0 → Enable=1, Bus=0x00, Dev=0x1F, Func=0x0, Offset=0xF0

Challenge 8: Firmware Rootkit Detection

Hard

You suspect a firmware rootkit. Identify the most reliable detection method that can't be fooled by OS-level compromise. Flag: FLAG{most_reliable_method}.

# Methods:
# 1. Hash comparison (flashrom dump vs vendor hash)
# 2. CHIPSEC whitelist (tools.uefi.whitelist)
# 3. Intel Boot Guard (hardware ACM verification)
# 4. Secure Boot violation detection
#
# Which can't be fooled by a rootkit controlling the OS?

Intel Boot Guard uses hardware (ACM in PCH) to verify firmware before any software runs. A rootkit can intercept flashrom SPI reads (method 1) or tamper with CHIPSEC (method 2), but can't modify fuse-burned Boot Guard values. FLAG{hardware_boot_guard}.

Challenge 9: UEFI Variable Tampering

Medium

An attacker with root wants to disable Secure Boot via UEFI variable modification. What protects the variables? Flag: FLAG{protection_mechanism}.

# Attempt:
efivar --name 8be4df61-...-SecureBoot --write --data=0x00
# Result: Permission denied (authenticated variable)
#
# Secure Boot variables use authenticated writes:
#   EFI_VARIABLE_TIME_BASED_AUTHENTICATED_WRITE_ACCESS
#   Requires valid PKCS#7 signature rooting to PK/KEK

Writes must include a valid PKCS#7 signature chain. Without the PK/KEK private key, you can't forge signatures. FLAG{authenticated_variables}. However, entering Setup Mode (deleting PK) disables authentication.

Challenge 10: BAR Size Determination

Medium

After writing 0xFFFFFFFF to BAR0 and reading back 0xFFF00000, calculate the memory region size. Flag: FLAG{size_in_MB}.

# BAR sizing: write all 1s, read back, invert, add 1
# Readback = 0xFFF00000
# Mask type bits: 0xFFF00000 & ~0xF = 0xFFF00000
# Invert: ~0xFFF00000 = 0x000FFFFF
# Add 1:  0x000FFFFF + 1 = 0x00100000 = ??? bytes

0x00100000 = 1,048,576 bytes = 1 MB. The lowest set bit in the readback mask determines alignment and size. FLAG{1}.
