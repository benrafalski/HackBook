V8 Compilation Pipeline

JavaScript source goes through multiple tiers of increasingly optimized compilation:

Source JS
  │
  ▼
Parser ──▶ AST (Abstract Syntax Tree)
  │
  ▼
Ignition ──▶ Bytecode (interpreted, collects type feedback)
  │
  ▼
Sparkplug ──▶ Non-optimized machine code (fast baseline, no IR)
  │
  ▼
Maglev ──▶ Mid-tier optimized code (SSA-based, fast compilation)
  │
  ▼
TurboFan ──▶ Fully optimized machine code (sea-of-nodes IR, speculative)

V8 Object Model — Maps & Hidden Classes

Every JS object has a hidden Map (aka hidden class/shape) that describes its structure: property names, offsets, and types. Objects sharing the same property layout share the same Map.

// Both objects share the same Map because same property order
let a = { x: 1, y: 2 };
let b = { x: 10, y: 20 };

// Different Map — property order differs
let c = { y: 2, x: 1 }; // Different transition chain!

Map Transitions

Map M0 (empty)
  │ add "x"
  ▼
Map M1 {x: @offset0}
  │ add "y"
  ▼
Map M2 {x: @offset0, y: @offset1}
  │ add "z"
  ▼
Map M3 {x: @offset0, y: @offset1, z: @offset2}

Transitions are shared: if two objects add the same properties in the same order, they follow the same transition chain and land on the same Map.

Property Storage Modes

ModeConditionStorageAccess Speed
In-objectFirst ~10 properties (fixed at allocation)Directly on JSObjectFastest
Out-of-object (fast)Properties beyond in-object slotsSeparate PropertyArrayFast
DictionaryToo many adds/deletes, or delete usedHash tableSlow
// Force dictionary mode
let obj = {};
for (let i = 0; i < 100; i++) obj["prop" + i] = i;
// or:
let obj2 = { a: 1 };
delete obj2.a; // Triggers map deprecation → dictionary mode

SMI Tagging & Pointer Tagging

V8 uses tagged values — the low bit(s) distinguish pointers from immediates:

Tag (low bit)MeaningFormat
0SMI (Small Integer)Value is shifted left by 1 (or 32 on 64-bit with compression)
1Heap pointerPoints to a HeapObject (subtract 1 to get raw address)
// In a 64-bit V8 with pointer compression:
// SMI 42 stored as:  0x0000002a00000000  (42 << 32)
// HeapObject ptr:    0x08040a21           (compressed, low bit = 1)

// Quick GDB check for SMI vs pointer:
// (gdb) x/xg $addr
// If value & 1 == 0 → SMI,  value >> 32 = integer
// If value & 1 == 1 → HeapObject at (base + value - 1)

HeapNumber

Doubles and integers outside SMI range are boxed as HeapNumber objects on the heap — an extra allocation and indirection.

let smi = 42;            // SMI — stored inline, no heap allocation
let big = 2 ** 31;       // HeapNumber — boxed on heap
let dbl = 3.14;          // HeapNumber — always boxed

V8 Heap Structure

V8 Heap Layout
┌─────────────────────────────────────────────┐
│ New Space (Young Generation)                │
│  ├── Semi-space "from" (inactive)           │
│  └── Semi-space "to"   (active)             │
│  Size: 1–8 MB (configurable)               │
│  GC: Scavenger (minor GC, very fast)        │
├─────────────────────────────────────────────┤
│ Old Space (Old Generation)                  │
│  ├── Old Pointer Space (objects with refs)  │
│  └── Old Data Space   (raw data, strings)   │
│  GC: Mark-Sweep-Compact (major GC)          │
├─────────────────────────────────────────────┤
│ Code Space                                  │
│  JIT-compiled machine code (RWX → RX)       │
├─────────────────────────────────────────────┤
│ Map Space                                   │
│  Map (hidden class) objects only             │
├─────────────────────────────────────────────┤
│ Large Object Space                          │
│  Objects > kMaxRegularHeapObjectSize         │
│  Each gets its own mmap'd page               │
└─────────────────────────────────────────────┘
SpaceContentsGC Strategy
New SpaceNewly allocated objectsScavenger (copy collector, ~1ms)
Old SpaceSurvived 2+ scavengesMark-Sweep-Compact (~10–100ms)
Code SpaceJIT codeMark-Sweep

Large Object SpaceLarge allocationsMark-Sweep (never moved)

Garbage Collection

Scavenger (Minor GC — Young Generation)

Uses Cheney's semi-space copying algorithm. Objects in the active semi-space are traced; survivors are copied to the other semi-space (or promoted to Old Space if they've survived 2 scavenges). Dead objects are implicitly freed.

# Trace GC events
d8 --trace-gc script.js

# Output example:
# [4321:0x5600] Scavenge 2.1 (6.0) -> 1.8 (8.0) MB, 0.8 / 0.0 ms
# [4321:0x5600] Mark-Sweep 14.2 (20.0) -> 10.1 (20.0) MB, 12.3 / 0.0 ms

Mark-Sweep-Compact (Major GC — Old Generation)

Mark: trace from roots (stack, globals, handles), mark reachable objects.
Sweep: iterate heap pages, free unmarked objects, build free lists.
Compact: relocate surviving objects to eliminate fragmentation.

// Force GC in d8 (with --expose-gc flag)
gc();               // Major GC
gc({ type: 'minor' }); // Minor GC (Scavenger)

// Trigger GC pressure for testing
let leaks = [];
for (let i = 0; i < 1000000; i++) {
  leaks.push({ data: new Array(100) });
}

Arrays in V8 — Elements Kinds

V8 tracks the type of elements stored in arrays via elements kinds. Transitions only go in one direction (more specific → more general) and never reverse.

Elements KindDescriptionPerformance
PACKED_SMI_ELEMENTSDense array, all SMIsFastest
PACKED_DOUBLE_ELEMENTSDense array, all doublesFast (unboxed)
PACKED_ELEMENTSDense array, mixed typesSlower (tagged)
HOLEY_SMI_ELEMENTSSparse array, SMIs + holesSlower (hole checks)
HOLEY_DOUBLE_ELEMENTSSparse, doubles + holesSlower
HOLEY_ELEMENTSSparse, mixed + holesSlowest
DICTIONARY_ELEMENTSHash table backedSlowest
Transition lattice (one-way only):

PACKED_SMI ──▶ PACKED_DOUBLE ──▶ PACKED_ELEMENTS
    │                │                  │
    ▼                ▼                  ▼
HOLEY_SMI  ──▶ HOLEY_DOUBLE  ──▶ HOLEY_ELEMENTS
// Start as PACKED_SMI_ELEMENTS
let a = [1, 2, 3];

// Transition → PACKED_DOUBLE_ELEMENTS (irreversible)
a.push(1.1);

// Transition → PACKED_ELEMENTS (irreversible)
a.push("hello");

// HOLEY transition — creates hole at index 99
let b = [1, 2, 3];
b[99] = 4;   // Now HOLEY_SMI_ELEMENTS

// Check with d8:
// d8 --allow-natives-syntax
// %DebugPrint(a);  → look for "elements kind" in output

JIT Compilation — TurboFan

TurboFan is V8's top-tier optimizing compiler. It uses a sea-of-nodes intermediate representation and relies heavily on type feedback collected by Ignition.

Speculative Optimization

TurboFan speculates based on observed types. If a function always received integers, TurboFan emits optimized integer arithmetic. If the speculation is wrong at runtime, it deoptimizes (bails out back to Ignition bytecode).

function add(x, y) {
  return x + y;
}

// Warm up with integers — TurboFan speculates integer addition
for (let i = 0; i < 100000; i++) add(i, i);

// Now pass a string — type guard fails → deoptimization!
add("hello", "world");
# Observe optimization and deoptimization
d8 --trace-opt --trace-deopt script.js

# Output:
# [marking add for optimization]
# [completed optimizing add]
# [deoptimizing (DEOPT eager): ... not a Smi]

TurboFan Sea-of-Nodes IR

# Generate TurboFan IR graphs (JSON for Turbolizer)
d8 --trace-turbo script.js
# Creates turbo-*.json files → open in Turbolizer

# Turbolizer: https://v8.github.io/tools/turbolizer/
# Visualizes: control flow, data flow, effect chain
# Key node types:
#   NumberAdd, SpeculativeNumberAdd  — arithmetic
#   CheckSmi, CheckMaps             — type guards (deopt on fail)
#   LoadField, StoreField            — property access
#   FrameState                       — snapshot for deoptimization

Deoptimization

When a type guard (CheckSmi, CheckMaps, etc.) fails, V8 uses the FrameState nodes to reconstruct the Ignition frame and resumes interpretation. Repeated deopt → function is marked "don't optimize."

// Force optimization with native syntax
// d8 --allow-natives-syntax

function vuln(arr, idx) {
  return arr[idx];
}

%PrepareFunctionForOptimization(vuln);
let a = [1, 2, 3];
vuln(a, 0);
vuln(a, 1);
%OptimizeFunctionOnNextCall(vuln);
vuln(a, 2); // Runs optimized

// CheckBounds node was emitted based on array length speculation
// If bounds check is removed by a bug → OOB access

Pointer Compression & V8 Sandbox

On 64-bit, V8 compresses heap pointers to 32-bit offsets from a 4GB-aligned base address (the cage). This halves memory usage for pointers.

# Pointer compression layout
Base register (e.g., r13 on x64) = cage base (4GB aligned)

Full address = cage_base + compressed_pointer
             = 0x1234_0000_0000 + 0x08040a21

# The cage constrains all heap pointers to a 4GB region
# External pointers (ArrayBuffer backing stores) use an
# External Pointer Table (EPT) — indices instead of raw pointers

V8 Sandbox (Ubercage)

The V8 sandbox reserves a large virtual address region (~1TB) containing the 4GB pointer compression cage plus regions for external pointer tables, code, and WASM memory. Goal: prevent an attacker with arbitrary R/W inside the cage from corrupting memory outside it.

ComponentInside Sandbox?Protection
JS objects, MapsYes (cage)Pointer compression
ArrayBuffer backing storesYes (sandbox)External Pointer Table (EPT)
Code objectsYes (code cage)Separate code pointer table
WASM memoryYes (sandbox)Guard pages
Process memory outside sandboxNoCannot be reached by corrupted ptrs

ArrayBuffer & TypedArrays

JSArrayBuffer object layout:
┌──────────────────────┐
│ Map pointer          │ → ArrayBuffer Map
│ Properties           │
│ Elements             │
│ byte_length          │ ← size of the buffer
│ backing_store ptr    │ ← points to raw memory (external or sandbox)
│ bit_field            │ ← flags (is_external, is_shared, etc.)
└──────────────────────┘

JSTypedArray (e.g., Uint32Array) layout:
┌──────────────────────┐
│ Map pointer          │ → Uint32Array Map
│ Properties           │
│ Elements             │
│ buffer               │ → backing JSArrayBuffer
│ byte_offset          │
│ byte_length          │
│ length               │ ← number of elements
│ base_pointer         │
│ external_pointer     │ ← direct pointer to data start
└──────────────────────┘
// Creating and inspecting
let ab = new ArrayBuffer(0x100);
let view = new Uint32Array(ab);

// In d8 with --allow-natives-syntax:
// %DebugPrint(ab);
// → backing_store: 0x5555deadbeef
// → byte_length: 256

// TypedArray provides direct memory read/write to backing store
view[0] = 0x41414141;
// Writes 4 bytes at backing_store + 0

Exploit relevance: If you corrupt backing_store or byte_length, you get arbitrary read/write. Post-sandbox, these pointers go through the External Pointer Table.

Patch Analysis Methodology

V8 vulnerabilities are often disclosed through Chromium bug tracker and fixed via CLs (change lists). Analyzing the diff reveals the bug class and how to trigger it.

# 1. Find the CVE → Chromium bug → V8 CL
# Example: CVE-2024-XXXXX → https://crbug.com/12345
# CL link in the bug → https://chromium-review.googlesource.com/c/v8/v8/+/56789

# 2. Fetch the vulnerable and fixed versions
git log --oneline --all | grep "12.1.285"
git checkout <vulnerable_commit>^  # One before the fix

# 3. Read the diff
git diff <vulnerable_commit>^ <fix_commit> -- src/compiler/

# 4. Key things to look for in the diff:
#    - Missing bounds check → OOB
#    - Wrong type check / CheckMaps removal → type confusion
#    - Incorrect range analysis → integer overflow in bounds
#    - Missing write barrier → GC corruption
#    - Turbofan reducer bugs → incorrect optimization

# 5. Common vulnerable components:
#    src/compiler/simplified-lowering.cc   — range/type narrowing
#    src/compiler/typer.cc                 — type inference
#    src/compiler/js-call-reducer.cc       — builtin inlining
#    src/compiler/effect-control-linker.cc — lowering phase
#    src/builtins/                         — builtin implementations

# - External pointers go through the External Pointer Table (EPT)
# - Code pointers go through the Code Pointer Table (CPT)
# - WASM memory is inside the sandbox

# With arbitrary R/W inside the sandbox, you can:
# [X] Corrupt JS objects          → but still inside cage
# [X] Read/write ArrayBuffers     → but backing store is in sandbox
# [X] Corrupt EPT entries         → entries are tagged, type-checked
# [?] Corrupt WASM instance data  → potential escape vector
# [?] Corrupt JIT code            → code is in code cage with CPT
# [?] Signal handler abuse        → race condition based

# FLAG: FLAG{wasm_instance_corruption}

Key escape vectors (as of 2024-2025):
1. WASM instance data corruption: Overwrite the WASM instance's imported function table or indirect call target to redirect control flow outside the sandbox. WASM instances contain pointers to native code that can be corrupted.
2. Signal handler manipulation: Race between signal delivery and handler registration — less reliable but doesn't require WASM.
3. JIT code page corruption: If you can write to code pages (bypassing W^X), you inject shellcode directly — but V8 now uses a Code Pointer Table to prevent this.
The V8 security team continuously hardens these vectors. Check chromium.googlesource.com/v8/v8/+/main/src/sandbox/ for latest mitigations.
